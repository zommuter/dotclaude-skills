**THE ARGUMENT FOR MASKING.** The lane SSOT already carries `mask_backticks`
(`lib-lane-anchor.sh:92`) for exactly this, and `PARKED-POOL-LANE` uses it via
`leading_lane_run`. A backticked token is prose by markdown convention; treating it as a
control marker is the tool reading documentation as configuration.

**THE ARGUMENT AGAINST, which is why this is not a one-liner.** `classify-repo`'s own
`id:4da4` note says first-occurrence is what makes it robust *"where a title-scope +
backtick-strip is not"* -- it cites `leAIrn2learn id:c3f5`, a `[HARD - pool]` item with a
backticked `[ROUTINE]` 1,600 chars into its handback history, where **16 desynced backticks
let the strip miss it** and it mis-fired execute. So backtick-stripping was TRIED, failed on
real data, and first-occurrence was the deliberate replacement. Re-introducing masking
without addressing desynced backticks re-opens a closed defect.

Note `f447` would not have been fixed by masking either -- its mention is unbackticked.
Masking is not sufficient for the observed population, which is itself an argument that the
right answer may be neither masking nor nothing.
