## A CONCRETE INSTANCE, observed here 2026-09-08, hours after this item was ingested

The item arrived in the inbox at ~09:20 and the hazard it describes fired at ~10:05 in this
same repo, in a sharper form than the item states. Recorded because a named mechanism is
worth more than a general principle, and because this one is silent.

**What happened.** The relay integrator (this session) had a `--no-ff` merge of
`relay/helperfix-exec` IN PROGRESS: `MERGE_HEAD` set, a `TODO.md` conflict resolved and
staged, awaiting `git commit`. A parallel session working the censor items ran its own
`git commit` in the same working copy. Because a merge was in progress, **its commit became
the MERGE COMMIT** -- absorbing the integrator's staged merge resolution under the parallel
session's message.

The result is `f202a461`, whose two parents are `9201732b` (the parallel session's gitignore
commit) and `8c7e0893` (the integrator's hardening branch), but whose subject reads
`ledger: re-measure id:d29b, file id:6740 (handover docs now have no backup)`. Nothing in that
message mentions the merge, the branch, or the three items it closes.

**Nothing was lost, which is the trap.** Verified after the fact: the hardened
`tests/lib-workflow-check.sh` is on `main`, all three of `id:1b0e`/`id:e044`/`id:ad67` are
`[x]` in BOTH ledgers, and the full suite is `597 passed, 0 failed, 0 errored, 8
expected-red`. A collision that corrupted content would announce itself. This one produced a
correct tree with a misleading history, so the only symptom is a commit message that
describes the wrong work -- and `git log --oneline` is exactly where a later session goes to
ask "what closed these items?".

**Why the existing guards did not catch it.** The relay repo lease (`claim.sh`) WAS held
throughout, as `relay-manual2-138800b0`. It guards relay dispatch; it does not and cannot
stop an ad-hoc session's `git commit` in the same checkout -- which is precisely this item's
point, now with a witness. The `verify-isolation.sh` gate passed legitimately: the child's
worktree was clean and one commit ahead. Isolation of the CHILD was never the problem; the
integrator's own index was the shared surface.

**What this adds to the item as filed.** "Take an advisory claim" would not have prevented
this on its own, because the colliding action was a bare `git commit` by a session that had
no reason to think it was inside anyone's merge. The sharper rule is about the WINDOW: a
repo with `MERGE_HEAD` set is mid-transaction, and any `git commit` by anyone lands INTO that
transaction.

**ROOT CAUSE, from the colliding session itself -- and it is sharper than the paragraph
above.** Amendment declared 2026-09-08 (per the README notes-are-editable rule); nothing
above was deleted. The other session diagnosed its own step and the finding is better than
the inference drawn from outside it:

> "Not a race I lost -- a helper I skipped. At that step I used a bare `git add` + `git
> commit` instead of the flock'd `commit-ledger.sh` I had correctly used minutes earlier for
> `819d009c`."

So the mechanism was never a gap in the tooling. **The flock'd helper already prevents this**
-- `commit-ledger.sh` is scoped and locked, and had it been used at that step the collision
could not have occurred. The session knew the helper, could reach it, and had just used it
for the same class of write.

**That is an argument for a GUARD, not for documentation.** The colliding session's own
conclusion, and it is the right one: a bare `git commit` is *always available and nothing
stops it*. A rule that says "use the helper" is obeyed exactly as often as it is remembered,
and this incident is what forgetting once looks like -- from a session that was otherwise
following the convention correctly. Weigh the fix accordingly: a `pre-commit` hook that
refuses a bare commit in a shared relay checkout while `MERGE_HEAD` is set costs almost
nothing and is not defeatable by forgetting. Documentation here would be a rule about a rule.

The two structural options remain worth considering alongside it -- (a) make the in-progress
merge visible to other sessions, (b) keep integrator merges off the shared checkout entirely
-- but both are larger changes than the guard, and neither is needed to close the specific
hole this incident found.

**Agreed protocol, in force between the two sessions from 2026-09-08.** Every ledger write
goes through `md-merge.py` / `commit-ledger.sh`, no bare `git commit` in a shared checkout;
plus `git rev-parse -q --verify MERGE_HEAD` as a cheap backstop before committing. That is a
convention between two live sessions, NOT a mechanism -- which is exactly why the guard above
is still worth building.

**History was deliberately NOT rewritten.** The content is correct and the parallel session's
own work is inside the same commit; rewriting to fix a message would be a destructive
operation on another session's commits to buy cosmetics. Recorded here instead, which is what
the note is for.
