## The finding

No mechanism exists for a coordinated multi-session shutdown. On 2026-09-09 it was done by hand:
`ListAgents` to enumerate peers, a relayed ask to each, and a wait on each one's self-reported
DONE-done.

## Two owner-sketched shapes

1. An external `inotifywait` watcher over a marker directory.
2. Every session touches its own "I'm done" marker (or removes a "still active" one), and the last
   one out powers off.

## COMPOSE -- do not build new lockfile machinery

`relay/scripts/heartbeat.sh` already carries live-runs plus a TTL, and `claim.sh` already carries
mtime-TTL expiry. The precedent is `id:11c6`: a singleton guard built by composing `claim.sh`
rather than by minting a second locking primitive.

## Constraints that any design must satisfy

- **Both marker polarities fail SAFE but then STALL.** A crashed session leaves its marker, so
  nobody powers off -- correct, but one dead session then blocks shutdown forever. A TTL or a
  pid-liveness check is therefore mandatory, not optional.
- **`claim.sh`'s `pid` is the WRITER's pid, not the pool's**, so it is NOT a liveness check
  (see the `claim-pid-is-not-liveness` memory).
- **An idle notice CANNOT distinguish "between turns" from "finished".** A session waiting on
  background children goes idle repeatedly. Idle must never be the trigger. This is the hard
  constraint learned in the incident.
- **`ListAgents` lists peer SESSIONS but not workflow children**, and its `type` field is not
  authoritative for them -- so enumeration alone cannot establish that everything has stopped.
