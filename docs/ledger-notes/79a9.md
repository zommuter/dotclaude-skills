## From TODO

**A handback leaves the ROADMAP box unticked -- correctly, the work is not done -- so the next
round's discovery sees the same open item and re-dispatches it. `repeatHandbacks`
(`relay-loop.js:4998-5016`) DETECTS this at threshold 2, classifies the route, logs the alert
and returns it in the result, and nothing in that path stops, deprioritises or otherwise alters
the dispatch.**

That is **detection with a no-op resolution** -- the `id:4d8e` anti-pattern this fleet already
has a rule for: *"a deterministic detector that FINDS a problem but whose resolution silently
no-ops is the anti-pattern"*, whose founding case was `unpromoted-scan` correctly reporting 17
untagged items while the handoff then promoted nothing. The loud detection is wasted because
the resolution is not forced. Same shape here: the operator gets a `repeat-handback ALERT`, and
the loop re-dispatches anyway.

**Two instances, both observed 2026-09-09:**
* `id:c381` dispatched in rounds 2 AND 3 of run `relay-20260909-125344-21396`, both handing
  back. Round 2's handback was constructive (context-budget size-out at 293,744 B, decomposed
  into seams `feec`/`2325`/`31c2`, no commits, clean worktree); round 3's died on the annex gate.
* `id:6df0` twice on the morning of 2026-09-09: one merged, one re-implemented **from a stale
  base** and refused at the gate. The reporting session diffed them, found them semantically
  identical, and discarded the duplicate. That is the cost made concrete -- a whole executor
  unit's Sonnet spend produced a duplicate of work already merged.

**OPEN QUESTION, carried across deliberately unresolved.** By round 3, `c381` was ALREADY
marked `🚧 GATED (auto, id:3801; route:hard-split)` in `ROADMAP.md` by round 2's own seam split.
A gated item should not have been selectable. Two candidate causes with very different blast
radii:
* **(a) a discovery-snapshot race** -- the gate landed after round 3's discovery snapshot was
  taken. Benign, and the same class as any read-then-act window.
* **(b) gate state is not consulted at selection at all** -- which would make EVERY auto-gating
  route (`hard-split`, `decision-gate`, `human`) **advisory only**, and would badly outrank the
  re-dispatch issue itself.

Round 4 then dispatched `id:1e06` rather than `c381`, which **FAVOURS (a) but does not prove
it** -- one observation of the gate being honoured is consistent with a race that simply did
not recur. The reporting session raised (b), then withdrew it unprompted when round 4 landed,
and explicitly asked that the withdrawal not be recorded as a closed verdict. It is not. **This
needs an inside-the-loop diagnosis, not a patch written from outside**; do not "fix" the race
until which cause is real has been established, because a fix for (a) would leave (b) intact
and silently reassuring.

**Why this is filed rather than fixed inline.** It is a `relay-loop.js` dispatch-path question,
and that file had four branches pending against it when the report arrived. An outside patch to
a selection path nobody has diagnosed is how a benign race becomes a masked bug.

**Acceptance is NOT specified here on purpose.** The right resolution depends on which cause is
real, and on a decision this note cannot make for the owner: whether a repeat handback should
deprioritise the item, hard-skip it for the run, or force a route change. `id:1432` already
owns the ALERT; this owns the missing resolution. Whoever takes it should start by answering
(a)-vs-(b), then bring the disposition question back.
