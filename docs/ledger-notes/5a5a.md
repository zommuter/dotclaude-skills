# id:5a5a -- the shared-inbox reconcile is a PROSE-ONLY obligation: `relay-loop.js` references neither `scan-routed` nor `inbox-scan-repo`, and skipping it is silent

Found by `code-lawless-c3` while checking whether a live pool of theirs could reach the
`id:0246` false-RESOLVED path on its own. It cannot -- and the reason is the finding.

## Measured, on the installed scripts

    grep -c scan-routed      relay/scripts/relay-loop.js  ->  0
    grep -c inbox-scan-repo  relay/scripts/relay-loop.js  ->  0
    grep -c inbox-done       relay/scripts/relay-loop.js  ->  0
    grep -c todo-inbox       relay/scripts/relay-loop.js  ->  0

So neither the `--all` dead-letter auto-filer (`relay/SKILL.md:442`, `id:1d3f`) nor the per-repo
inbox visibility check (`relay/SKILL.md:452`, `id:ce50`) is wired into the Workflow at any point.
Both exist ONLY as prose obligations discharged by whichever turn reads `SKILL.md` and complies.
The peer complied by hand at launch (`inbox-scan-repo.sh code.lawless`, printed nothing) precisely
BECAUSE the prose told them to -- which is the mechanism working exactly as far as an agent's
attention reaches, and no further.

## Two consequences, pulling opposite ways

**Containment (good, and it bounds `id:0246`):** nothing unattended can fire the `id:0246`
false-RESOLVED path, because nothing unattended runs `scan-routed.sh --apply` at all. The exposure
is exactly the human/LLM turns that follow the prose. That narrows `id:0246`'s blast radius and is
the reason it is not an emergency.

**The hole (bad, and larger than `id:0246`):** a turn that does NOT read the prose silently skips
the reconcile, and nothing notices. The inbox then accumulates un-drained routing with no signal.
Fixing the extractor in `id:0246` only helps on the turns where someone remembers to call the tool
-- so `id:0246`'s value is conditional on this item's answer.

## Why this is a known class here, not a new one

This is the `id:4d8e` detection-with-no-op-resolution shape and the "built, green, but
UNREFERENCED" pattern this repo has already been bitten by (`id:5367`/`id:2062` had zero
references from `relay-loop.js` while plans assumed them live; `id:ae08` is the wiring child).
The standing rule from that episode is literally `grep -c <script> relay-loop.js` before treating
a script as available -- and it has now caught a third instance. It is also the `id:7986` shape:
an obligation documented, unenforced, and wrong or skipped for an unknown length of time.

## The decision, which is NOT mine to take

Should invariant 1 be WIRED into the loop, or stay a front-door obligation?

* **Wire it.** Then the reconcile happens whether or not a turn reads the prose, and the
  mechanize-first rule is satisfied. Cost: the loop gains a cross-repo read of a LOCAL-ONLY store
  from inside a public-repo script, which must come in by injection (`$RELAY_INBOX`) and fail OPEN.
  It also puts a destructive-capable path (`--apply` calls `inbox-done`, which DELETES) inside the
  unattended pool, which is precisely what currently cannot happen. Doing this BEFORE `id:0246`
  and `id:d9ff` land would arm the false-RESOLVED path unattended -- strictly worse than today.
* **Keep it a front-door obligation**, but make skipping it LOUD rather than silent: e.g. the
  orchestrating turn records that it ran the check, and its absence is reported. Cheaper, keeps
  deletion attended, and matches the "reserve the LLM for loud failures" half of the rule.

**Recommendation: keep deletion attended, make the SKIP loud, and do not wire `--apply` into the
pool at all.** The reconcile's read half is safe to mechanize; its delete half is the one thing in
this cluster that is unrecoverable, and today's accidental containment is worth keeping on purpose.
Sequencing: `id:0246` and `id:d9ff` first regardless, since both fixes are prerequisites for
trusting any automation here.

That is a recommendation. The owner decides whether the invariant moves into the loop.
