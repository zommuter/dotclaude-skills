## Recurrence 2026-09-09 -- the observe-first gate has FIRED, and this time it blocked a review

Appended by the review child of run `relay-20260909-205831-5121`, which is the victim. Same
repo, same shape, 70 days later.

**What happened, in order.** The review child was dispatched with a pre-created worktree
(`id:34b7`), `~/.cache/relay/worktrees/dotclaude-skills/relay-20260909-205831-5121-review-repo-0`
on branch `relay/relay-20260909-205831-5121-review-repo-0`, and acquired the repo lease at
`21:21:50`. It ran the audit read-only for several minutes. Partway through, a `cd` into the
worktree failed with `no such file or directory`: the DIRECTORY and the BRANCH were both gone,
while `claim.sh peek` still showed this run holding the lease with that exact worktree path
recorded in the claim. The child re-provisioned via `provision-worktree.sh`; the replacement
was destroyed again within about a minute, branch included. Only the third attempt survived,
because it made an empty marker commit IMMEDIATELY after creation -- the workaround the 2026-07-01
entry above already describes.

**The 2026-07-01 root exposure is confirmed unchanged, and the mechanism is now named
concretely.** A review child is the worst case for it: it accumulates NO commits until its
ledger edits at the very end, so its branch tip equals `main` for essentially its entire
lifetime. During that whole window it is `git branch -d`-deletable and structurally
indistinguishable from an integrated leftover.

**New evidence the first instance did not have: the sweep is not merely ABLE to do this, a
shipped tool actively RECOMMENDS it.** `relay-doctor.sh`, run by this very child a few minutes
before the first reap, listed the child's own live worktree under:

    RETIRABLE RESIDUE (merged or unregistered -- no unmerged work, id:ba95):
      disposition: worktree-retire.sh <repo> <worktree-dir> <branch> --expect-merged
    dotclaude-skills  worktree  relay/relay-20260909-205831-5121-review-repo-0  ...
    4 retirable item(s) -- no work at risk; retire with worktree-retire.sh --expect-merged.

"no work at risk" was false at the moment it was printed. So the zero-commit inference is not
just a latent hazard in some cleanup path -- it is the published disposition of the health
tool, which any operator or automated reconcile is invited to act on.

**`id:7570` does not cover this.** That mechanism keeps a claim held past its TTL when the
worktree has commits beyond main. It is keyed on the same zero-commit predicate, so for a review
child it is inert for exactly the window in which the child is vulnerable. The lease being held
did not protect the worktree here, and was never consulted.

**What this changes for the decision.** The entry above closes "Observe-first: first logged
instance". That gate has now fired. The cost was again bounded only by the child noticing --
but it was NOT near-zero this time: two reaps, a re-provision each, and the review could not
have committed anything at all without the marker-commit workaround, because its branch kept
ceasing to exist. Of the two design questions posed above, the marker-commit-at-birth option is
now the cheaper one to evaluate: `provision-worktree.sh` already exists as the single
pre-dispatch creation point (`id:34b7`), so "make the tip differ from main from birth" is one
`git commit --allow-empty` in one place, and it closes the window structurally rather than
asking every present and future sweep to remember to consult the claim. That is an argument
about cost and blast radius, NOT a ruling -- the lane stays `[INPUT - meeting]` and the choice
between the two (or both) remains the owner's.
