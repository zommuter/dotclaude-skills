## From ROADMAP

**The Workflow runtime is STRICT mode -- MEASURED, not assumed -- so `workflow_node_check`'s
sloppy-mode wrapper is more permissive than the thing it models, and passes code that will
crash the pool.** Found 2026-09-08, resolving the open REVIEW_ME question left by the
`id:62c9` review.

**How it was measured.** The runtime is not in this repo, so it was probed directly: a
zero-agent Workflow script returning two independent sloppy/strict signals. Result, in 13 ms:

```json
{"thisIsUndefined":true,"typeofThis":"undefined","implicitGlobalThrew":"ReferenceError","verdict":"STRICT"}
```

Both signals agree. In sloppy mode a plain function call binds `this` to the global object
and an assignment to an undeclared identifier creates a global; in strict mode `this` is
`undefined` and the assignment throws `ReferenceError`. This replaces the review's honest
"could not check" with a fact.

**The consequence, also measured.** `tests/lib-workflow-check.sh` wraps the source in
`async function __relay_wf__(){ ... }` with no strict directive, making the body SLOPPY. A
file carrying strict-only syntax errors therefore passes the guard:

```
$ printf 'export const meta = {}\nfunction f(a, a) { return a }\nconst n = 0755\nreturn { n }\n' > strictonly.js
$ workflow_node_check strictonly.js; echo $?
0        # false GREEN
```

Duplicate parameter names and legacy octal literals are both SyntaxErrors under strict. The
runtime is strict. So the guard reports green on a file the runtime would refuse to parse --
the exact class of failure `id:62c9` exists to prevent, arriving through the opposite door.

**The fix is one directive, and it is safe on the live file.** Adding `'use strict';` to the
wrapper prologue catches the probe file (SyntaxError at the duplicate parameter), and the
REAL `relay/scripts/relay-loop.js` still parses cleanly under the strict wrapper -- verified
before proposing it, because a fix that reddens the live file would be worse than the bug.

**Why this was NOT a regression, which matters for how it is described.** Before the Node
upgrade a bare `node --check` resolved this file as CommonJS, which is also sloppy. So the
guard has never caught a strict-only error, and `id:62c9` did not introduce the gap -- it
inherited it while making the guard work at all. Do not record this as the executor's defect.
The `id:62c9` review named the question precisely and marked it unanswerable from this repo;
answering it took a probe nobody had run.

**Acceptance**: `workflow_node_check` rejects a file whose only defect is strict-only syntax
(duplicate params, legacy octal, `with`), while the pristine `relay-loop.js` and every
currently-migrated guard site stay green. **Done-check**: a spec case pinning the strict-only
rejection, plus a full `tests/run-tests.sh` green.

**Context**: `tests/lib-workflow-check.sh` (the wrapper prologue);
`tests/test_workflow_node_check_62c9.sh`; `docs/ledger-notes/62c9.md`. Sibling defects found
by the same review: `id:1b0e` (silent PASS on an unreadable file), `id:e044` (false refusal
on a line-initial `export`/`import` inside a template literal or block comment).
