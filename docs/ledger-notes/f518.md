## From TODO

**Nothing reaps a targeted STOP sentinel whose run never reached a dispatch decision.**
`STOP.relay-20260826-162405-7522` is 17 days old and has been carried forward unfiled by three
consecutive handovers.

## The mechanism, and why it is not a bug in `stop-sentinel.sh`

`stop-sentinel.sh` removes a sentinel as the **LAST act of a CONSUME**, deliberately: the
decision is logged and emitted first, so a failure after the decision leaves the sentinel to
re-fire next round rather than consuming it while the `|| stopRequested:false` fallback reports
no-stop. Stopping twice is harmless; silently not stopping is the failure that ordering guards
against. That is correct and must not be changed.

The gap is the case where **no consume ever happens**. A sentinel is written by
`stop-request.sh` against a live run; if that pool then dies, is `TaskStop`ped, or drains before
its next dispatch decision, the file is never read and never expires. There is no TTL and no
sweeper.

## Why it survived 17 days, and why it is still worth fixing

Harm is low **by construction**, and that is precisely why nobody minded: `id:cd94` made the
sentinel targeted (`STOP.<runId>`), so a leftover file cannot be stolen by, or false-stop, a
different pool. Before `id:cd94` this litter would have been actively dangerous.

Two things still make a cheap fix worthwhile:

1. **It destroys the readability of the surface.** Leftover litter is indistinguishable by eye
   from a live pending stop, so `ls ~/.config/relay/STOP*` no longer answers "is a stop
   pending?" -- the question an operator actually asks. `/relay stop --list` answers it properly
   (it resolves against live runs), but the directory listing is what people reach for.
2. **The un-targeted broadcast sentinel has the same missing reaper and IS dangerous.** A bare
   `~/.config/relay/STOP` written by `/relay stop --all` against a pool that then dies will
   false-stop **the next pool launched**, which is the exact failure `id:cd94` fixed for the
   targeted case and did not fix for the broadcast one.

## Shape of the fix

Reap a targeted sentinel whose runId is **absent from `heartbeat.sh live-runs`** -- the same
liveness source `stop-request.sh` already resolves against when it decides which pool to target,
and the same one that refuses (exit 3) when zero pools are live. Reusing it means **no new notion
of liveness is introduced**, so the reaper cannot disagree with the writer about whether a run is
alive (the `id:4347` two-tools-disagree class).

Open questions for whoever builds it: where the sweep runs (front-door preflight is the obvious
cheap site, since it already makes several such calls), and whether the bare broadcast `STOP`
can be reaped at all -- it names no run, so liveness cannot be keyed on it and it may need an
mtime bound instead.
