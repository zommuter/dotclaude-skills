### The defect

`cited_by`'s `elsewhere_lines` escape asks: does this reader's pattern also match something
the ledger STILL HOLDS after the move? If it does, the reader finds the same thing before and
after, so the move does not break it and the site is correctly dropped.

**That set is computed with only THIS block removed. A BATCH move is not modelled.**

So when many blocks move together -- which is the actual shape of a migration -- a pattern is
cancelled by text that is ITSELF about to be relocated. The reader is scored safe against a
ledger state that will not exist once the batch completes.

### Observed, and it silenced the one consumer that matters

On the 53-block corpus, `tracker/ledger-map.py:493` -- the only genuine continuation-body
consumer on this tree, the one whose existence justified the `id:1447` untraced amendment --
was SILENCED, because its `\*\*(Acceptance|Tests|Done-check|Context)\*\*` pattern matches
`**Context**` occurrences in OTHER blocks, all of which were also about to move.

That is the failure this item names: the escape is correct for a single move and wrong for a
batch, and the batch is the case we actually run.

### Not covered by the documented residue

`tools/ledger-continuations.py`'s docstring already discloses a related limit -- a `grep -c`
counting reader can be perturbed by a move this clears. **That disclosure does not cover this
case**, which is not about counting: it is about the surviving-text test being evaluated
against the wrong future state.

### What to build

Compute `elsewhere_lines` against the ledger state AFTER the whole batch, not after this block
alone. The mover already knows the full block set before it writes, so the information is
available; the escape simply asks the question too early.

Failing that, the escape must be disabled for a multi-block run and the sites reported --
refusing loudly beats clearing on a state that will not exist.

- **Acceptance**: in a multi-block move, a reader's pattern is cancelled only by text that
  SURVIVES the whole batch; `tracker/ledger-map.py:493` is reported against the 53-block
  corpus rather than silenced; and a single-block move behaves as it does today.

- **Done-check**: restoring all `## From ROADMAP` note bodies and running the mover reports
  `ledger-map.py:493` as a consumer of at least one block, where today it reports none.
