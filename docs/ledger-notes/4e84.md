# id:4e84 -- `classify-verdict.sh`'s strict rank order starves `hard` and `handoff` indefinitely

Inbound `routed:71c6` from `code.lawless`. Note created 2026-09-10 when the item was promoted to
`ROADMAP.md`; the ledger line carries the original report and is the authoritative statement of
the two faults.

## The mechanism, verified in code

`relay/scripts/classify-verdict.sh` builds its verdict as a single `if/elif` chain in strict
priority order. `hard` is rank 3 and `handoff` is rank 4, both `elif` branches sitting AFTER
`execute`. So while `actionable_routine_open >= 1`, neither can ever be reached.

Two distinct faults, as originally filed:

* **(a) an excluded-but-open item pins the verdict.** On `code.lawless` 2026-09-09, `id:b77b` was
  the ONLY actionable routine item and the dispatch brief forbade working it -- so `execute` won
  the branch and dispatched NOTHING, while 9 promotable TODO items sat unpromoted.
* **(b) strict rank order starves apex and handoff indefinitely.** 4 open `[HARD]` items including
  `id:8c1c` were never dispatched across 3 pools in a day, despite `--afk` and `STRONG_TIER=opus`
  permitting hard.

## THREE victims now, which is the argument for fixing the CHAIN rather than reordering a branch

This is the point that justifies promotion. The same `elif` has now starved three different things,
each discovered separately, by a different route:

1. **`hard` dispatch** -- the original report above.
2. **Review cadence.** The review-starvation incident was first diagnosed as lost-slot CONTENTION;
   the actual cause was one `elif` in this same file. Recorded in the memory
   `relay-execute-review-cadence-starvation`, whose standing note is that starvation there was
   TOTAL, not contention, and that `cc90`'s depth-K trigger was REFUTED.
3. **Promotion itself, found 2026-09-10.** `id:32c3` (build the `/inflownistration` skill) sat in
   `TODO.md` for ~3 weeks with its scope fully ratified, zero `gated-on:` edges, and zero presence
   in `ROADMAP.md`. Promotion happens ONLY in the `handoff` branch, so on this repo -- which always
   carries open ROUTINE items -- it was structurally unreachable. The owner asked why no pool had
   promoted it; the answer is this item.

Victim (3) has a self-referential consequence worth stating plainly, because it is the reason this
item was promoted BY HAND: **the promotion gap would have prevented the fix for the promotion gap
from ever being promoted.** The owner's own framing on authorising it: *"otherwise I bet it won't
happen either"*.

## A false premise a previous attempt already burned

A fix for this item was once proposed into a field that DOES NOT EXIST: `classify-repo.sh` has no
notion of a dispatch brief, so the proposed remedy for fault (a) had nowhere to live. That is
instance (1) of the six-instance error class recorded in `docs/session-handover-2026-09-09.md` --
reasoning from a source that does not record the thing being asked about. Before building, verify
against the code which inputs the classifier actually has; do not assume the brief is one of them.

## What the fix must NOT be

Not another branch reorder. Fault (b) is a property of strict total ordering over a chain where
several classes are simultaneously actionable, so promoting `handoff` above `execute` would simply
move the starvation onto `execute`. The shape that has been floated and is worth evaluating is a
chain-END re-ask (give the classifier a second pass for classes the first pass could not reach) or
a budget/round-robin across actionable classes. Both are design work, which is why this is `[HARD]`
and not `[ROUTINE]`.
