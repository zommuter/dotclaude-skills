# id:3f59 -- verify a claim against a session's own OBSERVABILITY surfaces, mechanically

`[INPUT - meeting]`. Filed 2026-09-10. The design question is what the MECHANISM is; the rule
itself is not in doubt.

## The evidence that makes this a mechanism question and not a prose question

Six instances in ONE evening (2026-09-09), across three independent sessions, of a single error
class: **reasoning from a source that does not record the thing being asked about, and reading
its silence as an answer.**

1. `classify-repo.sh` has no notion of a dispatch brief; a fix was proposed into a field that
   does not exist (`id:4e84`).
2. No workflow `journal.jsonl` records `agentType` -- 347 journals, 2 hits, both prose. An
   absence check there cannot tell you a run's launch config (`id:3846`).
3. `ListAgents` does not list workflow children UNTIL YOU MESSAGE ONE. The absence is CAUSED by
   not acting -- strictly worse than the rest.
4. An exit status read through a pipe (`cmd | head`, so `$?` is `head`'s). Caught twice, on
   different tools, by different people.
5. A lagging event log read as "nothing dispatched" while an Opus child was 143k tokens deep.
6. A token claimed to be "invented, with no source in any ledger" after grepping for a
   SURROUNDING PATTERN (`INTENSIVE[^]]*]`) and never for the token itself. It appears 19 times.

A seventh landed the same night: a `done/` directory that accumulates per-id artifacts across
runs, where a STALE `0ce2.json.error` from 2026-09-08 sat beside a fresh 2026-09-10 success
under the same id. "Is there an `.error` file for this id?" returns YES and means nothing.

**The decisive fact, and the reason this cannot be closed with more prose:**
`docs/ledger-notes/3846.md` already carried this as a standing METHOD WARNING, written by the
same author, hours before that author walked into instance (6). A warning whose own author trips
on it is evidence that the prose layer is saturated.

## The rule, in the framing worth adopting

The existing `~/.claude/CLAUDE.md` rule says: verify a claim about CODE against the code. This
extends it to a session's own observability surfaces -- an event log, an exit status, a reference
doc, an artifact directory, a registry listing. Each looks authoritative. Each is one hop from
the truth. The specific failure is not "trusting a source", it is **treating a source's SILENCE
as a negative finding without establishing that the source records that fact at all.**

## What the meeting has to decide

1. **Is any of this mechanizable, and which part?** Per the mechanize-first rule, the LLM should
   keep only what a mechanical layer genuinely cannot resolve, and those residuals must fail
   LOUDLY. Candidates, none of them obviously right: a lint for `$?`/exit-status-through-a-pipe;
   a convention that every artifact directory carries a run id in the FILENAME so a stale
   sibling cannot be mistaken for a fresh one (this one looks cheapest and most general); a
   required "does this source record this field at all?" step before any absence claim.
2. **Where does the residual LLM rule live so it is actually READ?** Six of twelve children in
   that cohort read no governing doc at all (`id:73a0`), and instance (6) shows a note's own
   author not re-reading it. A rule in a note is a rule nobody loads.
3. **What does the loud failure look like** when the mechanical layer cannot decide? A silent
   fallback here reproduces the bug class it is meant to catch.

## Explicitly NOT for this meeting

Do not let it become a review of the six instances. They are settled, recorded and corrected;
re-litigating them is how this becomes a second prose artifact instead of a mechanism.
