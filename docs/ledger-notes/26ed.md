# id:26ed — annex `.git`-symlink worktrees leaked again on quovadis, despite id:de4a

Routed in from a quovadis session as `routed:a5fc` (inbox), 2026-09-10, with the
owner asking for a global fix rather than a per-repo patch. Verified here before filing;
three of the incoming claims did not survive that check, and they are recorded below
because acting on them would have produced duplicate or wrong work.

## The actual open question

`id:de4a` ALREADY SHIPPED the exact fix the report proposes, on 2026-07-16:
`worktree-retire.sh:146-178` detects `-L "$wt/.git"`, proves the symlink resolves to THIS
repo's own admin dir for THIS worktree, rewrites it back to git's standard
`gitdir: <admin>` pointer, and only then proceeds to the normal dirty-check + removal.
It is force-free (`rm --`), non-destructive (pointer only), and defers loudly (exit 3) on
any symlink it does not recognise.

So the open question is NOT "what shape should the fix take". It is **why that
normalization did not fire on quovadis run `relay-20260910-165349-28261`**, which left two
verified-clean sized-out handback worktrees (id:8b1f shape: no commits ahead of main,
empty `git status --porcelain`) that auto-reap could not remove.

Candidate explanations, none yet confirmed:
- the reap path did not reach `worktree-retire.sh` for those two worktrees at all;
- the symlink did not resolve to the expected admin dir, so the guard deferred (this
  emits a `DEFER-UNRECOGNIZED-SYMLINK` line naming both paths -- check the reconcile log
  for the run before assuming otherwise);
- a regression since 2026-07-16.

**The residue is gone** (removed outside the reporting session), so this specific instance
is NOT reproducible. Next annex leak should be inspected BEFORE cleanup: capture
`readlink "$wt/.git"`, the expected admin dir, and the `relay-reconcile.log` lines for
that run.

## Fleet change that plausibly matters

`id:de4a`'s record states zkWhale was the ONLY annex repo among own repos as of
2026-07-16. Measured 2026-09-10, at least three are: `quovadis`, `code.lawless` and
`zkWhale` all have `annex.uuid` set and a populated `.git/annex`. Whatever assumption
de4a's testing rested on ("one annex repo, zkWhale-shaped"), it now covers more repos
than it was exercised against.

## Three incoming claims that did not survive checking

1. **"`git annex init` inside a linked worktree replaces `.git` with a symlink."** Wrong
   mechanism, and this repo already disproved it. Per `id:de4a`'s closure record, the
   symlink appears **immediately at `git worktree add`, before any annex command** -- it is
   `filter.annex.process` (the smudge filter). The `post-checkout`-hook hypothesis was
   tested and DISPROVED (hooks-disabled still produced the symlink). Filing this as
   annex-init-caused would send a fix at the wrong trigger.

2. **"Correlation held on every instance: symlinked `.git` <=> an `annex` entry in the
   worktree gitdir."** REFUTED on this tree, 2026-09-10. Of 9 relay worktrees, 8 carry an
   `annex` entry in their gitdir and only 1 of those 8 is symlinked -- 7 annex worktrees in
   the SAME repo (`code.lawless`) have a normal `gitdir:` file. Annex presence does not
   predict the shape. This matters for the fix: a detector keyed on annex-presence would
   fire on 8 of 9 worktrees, 7 of them wrongly. Keying on the `.git` SHAPE (`-L`), which is
   what de4a already does, is the correct predicate.
   Corroborating detail: the file-ok worktrees' `.git` mtimes are LATER than their annex
   symlink creation (e.g. `execute-f0de-0`: annex link 13:20:53, `.git` file 14:34:13), so
   the symlink state looks TRANSIENT -- rewritten back to a file by some later git
   operation. A reap that fires during the symlinked window fails; the same worktree may
   be reapable minutes later.

3. **"The failure is SILENT -- error code 10 never reaches RELAY_STATUS.md."** Half right,
   and the wrong half is load-bearing. Since `id:a290`, `reconcile-repo.sh`'s
   `report_retire_failure()` reports from the helper's EXIT STATUS in BOTH the reap and
   park loops, emitting a `REAP RETIRE FAILED` line to stderr and to
   `~/.claude/logs/relay-reconcile.log` with a per-exit-code disposition. It is true that
   it never reaches `RELAY_STATUS.md` -- but that is DELIBERATE, not an oversight:
   `reconcile-repo.sh:481-482` keeps this out of the emitted `actions`/`surfaced` JSON so
   the PLAN/APPLY parity oracle (`id:77ce`) stays byte-identical. Any "surface it in
   RELAY_STATUS.md" proposal must address that oracle first, or it will break a guard that
   exists to keep PLAN honest.

## Verification method (so this is re-checkable)

- `git worktree remove` refusal reproduced on a throwaway `mktemp -d` fixture (plain repo,
  no annex): converting a linked worktree's `.git` file to a symlink at the same target
  yields `fatal: validation failed, cannot remove working tree: '<wt>/.git' is not a .git
  file, error code 10`, exit 128; `git worktree prune -v` is then a silent no-op (exit 0,
  no output) and the worktree stays listed. So the mechanical core of the report is sound.
- Shape/annex cross-tabulation run over all 9 live relay worktrees.
- `id:de4a`, `id:a290`, `id:77ce`, `id:3016`, `id:2b7a` read at source, not from summaries.
