# id:45c8 -- two non-reproducing suite failures in one day, both with an agent writing the same checkout; ANNOTATE the run, do not guard it yet

Filed 2026-09-10. The deliverable asked for here is a **logger, not a guard** -- see "Why not a fix".

## The two observations

| run | reported failure | standalone re-run | concurrent writer in the tree |
|---|---|---|---|
| full suite, ~09:5x | `test_privacy_gate_prepush.sh` FAILED | PASSED, twice, exit 0 | yes -- a spec agent was writing `tests/test_chain_end_widen_verdict_set_4e84.sh` |
| `test_chain_end_widen_verdict_set_4e84.sh`, 1 of 3 runs | `HERMETICITY BREACH (id:b54b): relay/* ref or worktree drift` | did not reproduce in the two runs either side | yes -- `.claude/worktrees/agent-*` churn from other sessions |

Both tests touch git. Both passed immediately afterwards with no code change. Neither the agent nor
this session can prove causation, and both of us flagged rather than asserted it -- which is the
correct disposition and is recorded here so the next person does not inherit a guess as a fact.

## Why this is worth a line at all

The alternative reading is that we have two genuinely flaky tests, and that reading is WORSE: a
flaky test in a suite that gates `id:1048`'s auto-integrate (whose final gate is literally "full
suite GREEN in a scratch worktree") is a hole in a merge-to-main decision. Either way the question
"was this run clean?" currently has no recorded answer, and that is the actual gap.

Note the shape: this repo runs a ~5-minute suite that shells out to git, in a working tree that
background agents and peer sessions write concurrently. Nothing in a run's output says whether the
tree moved underneath it. A failure and a concurrent write are therefore indistinguishable from a
failure alone, after the fact -- and after the fact is the only time anyone looks.

## Why not a fix, and this is the repo's own rule

CLAUDE.md, **observe before preventing**: when considering a safety mechanism for a failure whose
frequency is unknown, build a logger first, gather evidence, then decide. n=2 in one day, during an
unusually agent-heavy session, is not a rate. Do NOT build a tree-lock, a serialisation gate, or a
retry -- a retry in particular would convert a real flake into a silent pass, which is the
`id:d35a` class.

Specifically do not reach for "make the suite refuse to run while the tree is dirty": the tree is
legitimately dirty for most of a working session, and that guard would block the normal case to
catch the rare one.

## What to build

`tests/run-tests.sh` records a cheap fingerprint of the working tree at START and at END of the
run, and annotates its summary line when they differ:

* fingerprint = `git status --porcelain` plus `git rev-parse HEAD` plus the `git worktree list`
  set, hashed. Cheap, no new dependency, no network.
* on a difference, append one line naming WHAT changed class-wise (tracked / untracked /
  worktree-set / HEAD), not a full diff.
* a clean run is annotated too, positively and briefly, so the absence of an annotation can never
  be mistaken for "no concurrency" (that is the read-silence-as-an-answer error class this session
  hit repeatedly -- see `id:3f59`).

Then a failure in an annotated-as-concurrent run is legible as such, and after a few weeks the log
says whether this is two coincidences or a pattern. THAT is when a guard gets designed, if at all.

## Acceptance

* A full-suite run whose tree is untouched throughout reports its summary plus an explicit
  clean-tree annotation.
* A run during which a file is created/modified/removed in the tree reports the summary plus an
  annotation naming the change class.
* The annotation NEVER changes the pass/fail verdict -- it is evidence, not a gate.
* No retry, no serialisation, no refusal-to-run is added.
