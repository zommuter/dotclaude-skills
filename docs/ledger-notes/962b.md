## From TODO

Successor to `id:bfd3`, dropped as proposed after the `id:cb3e` argument. The second mechanical
replacement, on the EXTRACTION axis.

### The defect

`extract_patterns` reads SOURCE TEXT and does not decode the reader language's string escapes.
So a genuine `existing.endswith('\n')` yields the **two-character literal backslash-n**, and
`literal=True` compiles it as such.

Verified directly against the live tool:

```
extracted literal: '\\n'   len= 2
```

The runtime argument is a NEWLINE. The extracted pattern is not. A newline test against a
single line is inert; a backslash-n literal is a real, and quite selective, content match.

### Why it matters, and why it is NOT the `bfd3` argument

This is the finding that refuted `bfd3`. That item assumed `\n` meant a newline and therefore
carried no ledger-distinguishing content. In fact the two-character literal matches ~0.15% of
ledger lines, making it MORE selective than 40 of the 49 sites -- and a planted reader whose
whole pattern was `\n` was demonstrated to be a genuine consumer that the proposed filter would
have silently cleared.

So the fix is not to judge the literal. It is to make the extracted pattern MEAN what the code
means. `relay/scripts/archive-closed.sh:381` is a genuine `.endswith('\n')` whose extracted
form is wrong; decoding fixes it correctly, and 8 sites with it.

### What to build

Decode the reader language's string escapes when a construct is in literal mode, so
`'\n'` becomes a newline, `'\t'` a tab, and so on -- per language, since shell single quotes do
NOT interpolate escapes while Python and JS do. Getting THAT distinction wrong would corrupt a
shell pattern, so it must be keyed on the reader's language, never applied blindly.

**A literal that cannot be decoded confidently stays as-is.** Failing toward the undecoded form
keeps the site IN, which is the loud direction.

- **Acceptance**: a Python or JS `'\n'` in literal mode extracts as a newline; a shell
  single-quoted `'\n'` still extracts as two characters; an undecodable literal is left
  unchanged rather than guessed; and every `id:9ce0` and `id:1447` floor property still holds.

- **Done-check**: `archive-closed.sh:381` and the other genuine `.endswith('\n')` sites stop
  appearing as content consumers of a single-line body, while a shell reader matching a literal
  backslash-n still does -- and the planted-reader case from the `bfd3` refutation is STILL
  named as a consumer, since that one is genuinely a two-character match.
