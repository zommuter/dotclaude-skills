IDEA: give each agent/session a copy-on-write union view over the canonical repo instead of (or alongside) a `git worktree`, so it sees the full tree in its own context and writes land in an upper layer. **WHERE IT GENUINELY WINS (2 dimensions, both real today):** (1) it DISSOLVES `id:34b7` part (2) — `provision-worktree.sh` exists only because a fresh worktree lacks the GITIGNORED build artifacts (`node_modules`, `.venv`, caches), so the parent symlinks them "best-effort" and its own header admits it is "deliberately NOT exhaustive"; loderite `RELAY_LOG.md:2681` (with `:3022/:3422/:3486`) shows children then REMOVING those symlinks again before commit. An overlay gives the complete tree for free, exhaustively, with COW writes — the provisioning step and the symlink-removal dance both disappear. (2) mounting the lower layer READ-ONLY is OS-level ENFORCEMENT of a read-only/pure-agent contract rather than a documented promise (the enforce-don't-document principle; relates the `id:23ab` formal-enforcement frontier). **WHERE IT DOES NOT HELP — record this so it is not re-litigated:** it does NOT address merge/semantic reconciliation, which is the actual bottleneck when several agents work one repo. Two agents editing the same file in two overlays conflict at merge exactly as in two worktrees; worktrees yield branches + real commits + `git merge`, an overlay yields a filesystem delta with NO history. Overlays improve the already-solved half (concurrent working state) and leave the hard half untouched. **BLOCKERS to settle BEFORE any build:** (a) the appealing property — SAME PATH, different content per agent — requires a per-agent MOUNT NAMESPACE (`unshare -m`); two processes cannot see different content at one path otherwise, and Claude Code's Bash tool does not launch agents in separate mount namespaces, so this needs harness support that does not exist today. Without it the overlay sits at a different path = a worktree with worse git integration, i.e. the idea loses its whole point. (b) `.git` semantics — if `.git` is inside the overlay, commits land in the UPPER layer's object store and are invisible to the canonical repo until `git fetch <overlaypath>`, which is worktrees-with-extra-steps; if `.git` is bind-mounted read-only the agent cannot commit at all. (c) privileges — overlayfs mount traditionally needs `CAP_SYS_ADMIN`; unprivileged overlay in a user namespace works on modern kernels (zomni is 6.18) and `fuse-overlayfs` is the rootless fallback, but that is a new dependency and a new failure mode. **RECOMMENDED SHAPE IF PURSUED:** do NOT frame it as replacing worktrees. Frame it as "overlay-provisioned worktree" — keep the git worktree for branch/commit/merge semantics, and use a union mount only to supply the gitignored artifact layer, which is (1) above and needs no mount namespace. That variant is buildable today and dissolves `id:34b7` part (2) outright. The full same-path per-agent view stays gated on harness mount-namespace support.
