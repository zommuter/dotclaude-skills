(owner request 2026-08-26) — today `--exclude`/`--priority`/`--only` are LAUNCH-time only (`args.excludeRepos`/`priorityRepos`/`onlyRepo`, consumed once before sharding), so changing a running pool's repo membership is impossible: the only levers are `/relay stop` (ends the run) or `TaskStop` (kills in-flight children and orphans their worktrees). The concrete need: an operator wants to work a repo BY HAND while the pool is live — this session hit it exactly, wanting to edit `dotclaude-skills` relay scripts while the pool held a `dotclaude-skills` execute lease, where the only options were 'wait' or 'stop the whole run'. **Prior art to reuse, not reinvent: the STOP sentinel family** (id:c012 / id:cd94 / id:a615) already solves every hard part — a per-`runId` TARGETED sentinel file (`~/.config/relay/STOP.<runId>`, never a global one, because parallel pools are the normal case and an unscoped file gets STOLEN by whichever pool reaches the check first), checked at **every dispatch decision** rather than only at a round boundary (a chaining round never reaches one — run `relay-20260822-154630-17003` made 14 dispatches all stamped `round=1`), consumed fail-safe with removal as the LAST act, and logged with `scope=`/`run=` so 'which pool did this affect?' is answerable after the fact. A `~/.config/relay/MEMBERSHIP.<runId>` sentinel (or an `inject.sh`-style control channel — id:baf1/354f already has a take-at-discovery hop) should follow that exact shape rather than invent a second protocol. **Semantics to settle:** (a) does a live-exclude take effect only at the next DISPATCH decision (leaving an in-flight unit for that repo to drain — almost certainly right, mirroring `/relay stop`), or must it also refuse the pending integrate; (b) does live-INCLUDE re-add a repo dropped at launch, or only one excluded live — re-adding a launch-excluded repo means it was never sharded/classified, so discovery must re-enumerate it; (c) does an unknown repo name LOUD-reject as the launch-time flags do (it should — id:d530's precedent); (d) does it write `relay.toml`? **It must NOT** — both `--exclude` and `--priority` are explicitly per-run and never mutate the registry, precisely because a session-kill would otherwise leave a silent permanent exclusion. Interacts with id:79fd: once discovery is continuous rather than round-barriered, a live membership set becomes MORE load-bearing, since there is no round boundary at which a relaunch could have applied a new one. <!-- id:9459 -->
