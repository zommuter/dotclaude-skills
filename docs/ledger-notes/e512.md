## From TODO

(observed live 2026-08-22, run `relay-20260822-154630-17003`). **What happened:** `lean4btc` was dispatched `mode=hard` at 13:52:51Z. The `RELAY_STATUS.md` snapshot written at 13:59:16Z placed it in NONE of `blocked / completed / inFlight / queued / skipped` and emitted the ⚠️ INCOMPLETE-ACCOUNTING banner naming it. The unit was fine — it integrated at 14:04:10Z as `relay-ckpt-20260822-1604`, pushed, `ids=e84c` — so the banner described a 6-minute window between the dispatch event and the integrate event during which the unit belonged to no section, NOT a lost unit. **Why it still matters, stated honestly:** during that window the unit genuinely WAS invisible, so if the pool had died there the work would have been unaccounted — the invariant is not wrong about the hazard. The defect is that it cannot distinguish TRANSIENT in-transition from TERMINAL lost, and reports both in the same alarming language ("a false clean"). An operator who sees this fire benignly a few times stops reading it, which is precisely this repo's own `id:4347` cry-wolf rule; and it cost a real investigation this session. **Prior art — read before designing:** the mixed-temporality problem is already known (`RELAY_STATUS` sections accumulate vs reset at different rates, which is why "every own repo in exactly one section" was already shown false); this is a NEW instance of that class, at the per-unit rather than per-repo level. **Suggested shape (not decided):** give a dispatched-but-not-yet-integrated unit an explicit in-transition state so it reaches a section by construction, OR keep the check but downgrade the wording when the unit has a dispatch event and no terminal event yet, reserving the "false clean" language for a unit with no live claim and no terminal event. Whichever way, the invariant must keep firing LOUDLY for a genuinely lost unit — do not fix the false positive by weakening the true positive. <!-- id:e512 -->
