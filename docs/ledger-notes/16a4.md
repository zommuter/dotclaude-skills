## The ask

Launch Claude Code so that it AND every descendant -- including detached / `nohup` / `setsid`
children -- share ONE hard memory and CPU cap:

```bash
systemd-run --user --slice=claude.slice --scope \
  -p MemoryMax=NG -p MemorySwapMax=0 -p CPUQuota=N% -- claude
```

cgroup v2 membership is inherited across fork/exec and cannot be escaped without cgroupfs
write access, so daemonizing does NOT get out of the cap.

Put the limit on a PERSISTENT slice -- a drop-in at
`~/.config/systemd/user/claude.slice.d/50-limits.conf` -- not on the scope, so it survives
and is tunable without editing the launcher.

## Gotcha to VERIFY EMPIRICALLY before relying on it

A nested `systemd-run --user --scope` defaults to `app.slice` and would create a SIBLING
scope that escapes the parent cap. Any inner wrapper (e.g. toesnail
`docs/dreamed/capped.sh`) must pass `--slice=claude.slice` explicitly, or the outer cap is
silently void. Confirm this by measurement, not by reading the manual.

## Done-check

`systemd-cgls --user-unit claude.slice` (or `cat /proc/<pid>/cgroup` for each) shows the
session AND a `setsid`-detached child in the same slice; `systemctl --user show
claude.slice -p MemoryMax,CPUQuota` reports the configured values. Escape probe: launch an
inner `systemd-run --user --scope` WITHOUT `--slice` and record whether its cgroup path is
inside or beside `claude.slice`; then repeat WITH `--slice=claude.slice` and assert it is
inside. Record both outcomes in this note before closing.
