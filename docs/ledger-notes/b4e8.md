## From TODO

— SKILL.md step 3b specifies `trap _relay_exit_teardown EXIT` installed in the front-door shell "immediately after minting `$RUN_ID` and before invoking the Workflow", with the explicit rationale that it must fire whether the Workflow RETURNS or DIES, because "a stderr line is the only signal left when the Workflow is SIGKILLed". But when the orchestrator is a Claude session, each Bash tool call is its OWN shell: a trap installed in the call that mints `RUN_ID` is gone before the Workflow tool is even invoked, and the Workflow runs in the harness, not under that shell. The trap therefore protects NOTHING in the session-driven path — which is the NORMAL path for every `/relay` a human types. **Observed 2026-08-18** (run `relay-20260818-200205-25179`, csgebra): the model had to run both teardown actions manually as an explicit post-step; had the session been killed mid-run, the run's heartbeat marker and every lease it held would have been left to expire on TTL alone, with no stderr line and no RELAY_STATUS row — exactly the SIGKILL case the trap was designed for. This is the `id:98f0` outage-watchdog's blind spot too, since a stale heartbeat is what it keys on. **Fix shapes**: move the two teardown actions into a small wrapper SCRIPT the front door invokes (so one shell spans mint→launch→teardown and the trap is real); or have the Workflow itself register its teardown so it is independent of the caller's shell lifetime; or make SKILL.md state plainly that in a session-driven front door the trap is inert and the two actions MUST be run as an explicit post-step. <!-- routed:83cf --> <!-- id:b4e8 -->
