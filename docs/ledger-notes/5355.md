# id:5355 -- `archive-done.sh` archives items completed IN THE CURRENT SESSION

Adopted from the shared inbox `routed:3b3a` by the chain-end review of run
`relay-20260905-113859-5807` (2026-09-05). It had been sitting as a dead-letter:
`relay-doctor`'s `scan-routed` reported it absent from this repo's `TODO.md`/`ROADMAP.md`.

## The defect

`todo-update/archive-done.sh`'s `if line.strip() in prior_done: ym = today_ym` branch (script
~line 107) archives any `[x]` line present in the PRIOR COMMIT, regardless of the item's own
date. The mandated skill order guarantees that condition is met for work just done:
`git-diary-workflow` Step 1 commits, then Step 3 runs `todo-update`, so this session's
just-committed `[x]` items ARE in the prior commit.

Observed 2026-09-04 in lodelore: `id:b0a0` and `id:3cd8`, both dated the same day, were
archived on the run that followed their own commit; restored by hand.

## Harm beyond tidiness

It moves `routed:XXXX` breadcrumbs OUT of `TODO.md`. The cross-repo twin-guard
(`scan-routed.sh`, `append.sh inbox-done`) scans only `TODO.md`/`ROADMAP.md`, so a
same-session close can be re-read as a dead letter -- and `inbox-done` REFUSES (exit 3)
without the twin, so the inbox entry can no longer be drained.

## Suggested fix (from the report; not ratified)

Exempt entries whose own `on YYYY-MM-DD` date is newer than the cutoff from the `prior_done`
branch -- let an explicit recent date beat the prior-commit heuristic.

## Acceptance

An `[x]` item carrying a trailing `on YYYY-MM-DD` date newer than the archive cutoff is NOT
archived, even when that exact line is present in the prior commit. An `[x]` item that is
genuinely old (no recent date, or a date older than the cutoff) still archives exactly as
today.

## Done-check

New `tests/test_archive_done_same_session_5355.sh`, hermetic in a `mktemp -d` repo: commit a
`TODO.md` containing an `[x]` line dated TODAY, then run `archive-done.sh` against it and
assert the line is STILL in `TODO.md` and absent from `TODO.archive.md`; second case, an
`[x]` line dated 60 days ago under the same prior-commit condition, assert it IS archived.
Then full `tests/run-tests.sh` green.

## Live confirmation 2026-09-07 (in THIS repo, not only lodelore)

Reproduced on our own tree during `/relay human --all`, minutes after the inbound report
was ingested. `id:2964` was closed and committed in the session, then the mandated
`todo-update` step ran `archive-done.sh TODO.md` and it **archived that same-session close
immediately** -- `TODO.md` -1 line, `TODO.archive.md` +1, for an item ticked minutes
earlier and dated the same day.

This is the exact mechanism the inbound report names: the `line.strip() in prior_done`
branch dates an entry `today_ym` regardless of its own date, and the mandated skill ORDER
(git-diary-workflow Step 1 commits, then Step 3 runs todo-update) guarantees this session's
just-committed `[x]` items ARE in the prior commit. So the defect is not lodelore-specific
and not rare: it fires on every same-session close in every repo that follows the standard
post-prompt skill order, which is all of them.

**Not restored by hand here, deliberately, and the reason narrows the item's severity.**
`id:2964` carries no `routed:` marker, so the cross-repo twin-guard harm the report
identifies as the concrete consequence does not apply to this instance -- the item is
genuinely done and its archived home is correct, just reached a month early. Restoring it
would be churn. What this instance adds is the FREQUENCY evidence: the report inferred the
mandated-order guarantee, and this confirms it end-to-end on a second repo.

The suggested fix stands unchanged: exempt entries whose own `on YYYY-MM-DD` date is newer
than the cutoff from the `prior_done` branch, i.e. let an explicit recent date beat the
prior-commit heuristic.
