# id:206e -- `archive-done.sh` should refuse to sweep a closed line whose `routed:` source is still open (the better invariant `id:1d83` did NOT build)

Filed 2026-09-10 as the explicit carry-forward of `id:1d83`'s fix **(1)**, so that closing `1d83`
does not silently drop it. `id:1d83`'s own note calls this *"the better invariant"*; the
adversarial review flagged that nothing tracked it and that `1d83`'s title frames the defect as
the `archive-done.sh` date guard, which the shipped fix does not touch at all.

## What `id:1d83` actually fixed, and what it did not

* FIXED: the twin CHECK is now archive-aware, so an archived breadcrumb is still found and
  `inbox-done` no longer refuses. The harm is gone.
* NOT FIXED: the archiver still sweeps an undated `[x]` line the moment it is in the prior commit,
  including one carrying a live `routed:` breadcrumb. The `id:5355` guard keys on an explicit
  trailing DATE, so an undated same-session close has no protection -- and the mandated
  `git-diary-workflow` -> `todo-update` order guarantees the prior-commit branch matches.

So the breadcrumb still LEAVES the live ledger earlier than anyone intends; it is simply no longer
fatal. That is a weaker resting state than not moving it, for two reasons worth stating:

1. A human or agent greping `TODO.md` to ask "did this route land?" still sees nothing. Only the
   machine predicate was taught about archives.
2. It puts the breadcrumb somewhere a future compaction pass could prune further. `id:1d83`'s
   widening accepts a record that has already been archived out of the live ledger, which moves
   the boundary of what "twin" attests -- the handoff agent flagged exactly this, and it is the
   reason the control case in `tests/test_inbox_twin_archive_1d83.sh` is load-bearing.

## Shape of the fix

In `todo-update/archive-done.sh`, a `[x]` line carrying a `routed:XXXX` marker is held back while
that token's inbox line is still OPEN.

Three constraints, each of which has already bitten something in this repo:

* The inbox path must come in by INJECTION (`$RELAY_INBOX`), never hardcoded -- `archive-done.sh`
  is a public-repo script and the inbox is local-only to public repos.
* It must fail OPEN: if the inbox cannot be read, archive NOTHING on that basis rather than
  guessing. An archiver that silently keeps everything is a visible annoyance; one that silently
  discards a guard is `id:d35a`.
* It must not re-grow the `id:0d7c` ledger-size problem. A held-back line is a LIVE ledger line,
  so the hold has to end: when the inbox line resolves, the next pass archives it normally.

## Open question the owner should settle first

Is this worth building at all now that the harm is fixed? The honest case against: `id:1d83`
removed the only mechanical failure, the measured backlog of archive-stranded twins is ZERO (this
session's census plus the review's, independently), and every extra cross-repo read in a
public-repo script is a new coupling. The case for: it restores "a live breadcrumb lives in the
live ledger" as a property rather than a coincidence, and it is the invariant `1d83`'s note
preferred on its own reasoning.

Recommendation: DEFER until something actually needs it, and keep this item as the record of a
known, deliberate gap rather than building a cross-repo coupling on a zero-instance backlog. That
is a recommendation, not a decision.
