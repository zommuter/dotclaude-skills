# id:9635 -- the relay-mech cgroup cap does not contain `llama-swap`, so an `[INTENSIVE]` local-llm recipe is effectively uncapped

Inbound `routed:4887`, ingested 2026-09-10 by review `relay-20260910-114832-18641` (dead letter:
in the shared inbox, absent from this repo's ledgers and archives).

## Measured live, not inferred

Confirmed 2026-09-10 by `ai-codebench` `id:0ce2`: the relay-mech cgroup cap bounded only the
**~378 MB HTTP client**, while `llama-swap` -- a **root service in `system.slice` with
`MemoryMax=infinity`** -- loaded the **~17.3 GiB** model in its OWN cgroup. The machine went into
swap and **two session processes were killed**.

## Why the cap cannot work as placed

The cap is applied to the process the relay launches. The memory is allocated by a long-lived
system service that the launched process merely talks to over HTTP, so the allocation happens
outside the capped cgroup by construction. No tightening of the client's own limit can change
this; the containment boundary is in the wrong place, which is why this is a design question and
not a number to lower.

## What it blocks

Unattended promotion of the **22 GB sibling recipes `8c1d` and `3ee7`**. Until the boundary
question is settled, an `[INTENSIVE - local-llm]` recipe's serially-alone guarantee bounds
CONTENTION but not FOOTPRINT, and the `[INTENSIVE]` tag's whole premise (per `conventions.md`:
these loads "must never overlap and must never sneak into a parallel wave") is only half
delivered.

## Options, none chosen here

Capping `llama-swap` itself is a change to a **root systemd unit**, i.e. a host modification that
is the owner's to make, not a relay child's. Refusing to launch while free memory is below the
model's known footprint is a relay-side guard that needs no root. Which of those (or both) is
right is the decision this item carries.

## Acceptance sketch

A launched local-llm recipe either cannot exceed a declared memory ceiling INCLUDING the model
server's own allocation, or is refused before launch with the shortfall named -- and the
behaviour is pinned by a test that does not require loading a real model.
