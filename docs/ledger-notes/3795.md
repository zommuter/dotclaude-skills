### The defect

`relay/scripts/unpromoted-scan.sh`'s `primary_lane()` requires the lane tag to cluster
IMMEDIATELY AFTER the title. Its own comment says so: *"any bracket-token further right is
prose/history and must NOT set the lane"*.

`tools/ledger-shrink.py` plants the `-- detail:` pointer BETWEEN the title and any lane tag
that had been in the body. So the trim moves the lane tag out of the only position
`primary_lane()` will read.

Minimal repro, run against the real function:

```
- [ ] **Some title** -- detail: `docs/ledger-notes/9999.md` [HARD] <!-- id:9999 -->   ->  lane=[]
- [ ] **Some title** [HARD] some prose <!-- id:9999 -->                               ->  lane=[[HARD]]
```

### Measured on this repo's live ledger, not on a fixture

Running the real scanner: **60 rows carry a lane tag AFTER the pointer, and 18 of them
disposition as `surface`** rather than their actual lane. Eight lose an EXECUTABLE lane
(`[HARD - pool]` x3, `[ROUTINE]` x4, `[HARD]` x1), demoting `promote` to `surface`.

**That can flip a repo's verdict.** `promote > 0` yields `handoff`; `surface > 0 AND
promote == 0` yields `human`. So the trim can silently convert pool-executable work into a
human question. This is the `id:4b64` failure class the script's own comments already
document, arriving through a new door.

### Scope, checked by running rather than reading

- `classify-repo.sh` is **IMMUNE** -- `id:4da4` takes the first `LANE_TAGS` hit ANYWHERE on
  the line, which is why its A/B output was byte-identical.
- `leading_lane_run()` in `lib-lane-anchor.sh` is **IMMUNE** -- the leading run sits before
  the title, ahead of the pointer.
- `primary_lane()` is the ONLY broken lane parser.

### Two candidate fixes, pointing opposite ways

1. `primary_lane()` skips a `-- detail:` pointer when locating the post-title lane cluster.
2. `ledger-shrink.py` plants the pointer AFTER the trailing lane run.

Fix 2 changes emitted output for every repo and interacts with the `lane-would-change`
invariance refusal; fix 1 is local to one parser. Not decided here.

- **Acceptance**: an item whose lane tag follows the detail pointer resolves to that lane;
  the 18 currently lane-dark items disposition correctly; and no item that legitimately
  mentions a lane token in PROSE gains a lane it does not own.

- **Done-check**: the minimal repro above returns `[HARD]` for both spellings, and the live
  scanner's `surface` count drops by the 8 executable-lane items while `laned` and `promote`
  absorb them.
