# id:1975 -- the TEST SUITE drained the live relay injection queue (re-scope of routed:1d58)

Inbound `routed:1d58` from `code.lawless`, **re-scoped on filing**. Their inbox line read
"the discovery-producer daemon consumed and DROPPED 19 injected review units". The 19 units and
their loss are real; the attributed cause is not. Both sessions re-verified and agree. Fixed
2026-09-10.

## What actually happened

`tests/test_prelude_mechanized_86a2.sh` executes `relay/scripts/discover-prelude.sh`, whose
step 6 is a **CONSUMING** `inject.sh take`. `inject.sh` resolves its queue from `$INJECT_BASE`
(default `~/.config/relay`), and that test isolated `RELAY_TOML` and nothing else. So every
`make test` drained the REAL global injection queue into `inject.done/`. Consumed injections
have no re-enqueue path, so they were lost from both the inbox and the ledger.

The 19 were the daemon-injected review units for completed `[MECHANICAL]` runs: 18 `code.lawless`
OCR sweeps plus `ai-codebench` `0ce2`.

## Why the first diagnosis went to the wrong component, recorded because the trap is general

The discovery-producer was the only entry in `~/.config/relay/heartbeats/` and its systemd run
(07:34:18-07:37:13) bracketed the take (07:35:35). Heartbeat correlation is not causation, and
`grep -c inject relay/scripts/discover-repos-mechanical.sh` returns **0** -- the producer cannot
take anything. This is the 2026-09-09 error class again (see `id:3f59`): an authoritative-looking
surface consulted for a question it does not answer.

What settled it: `repos=2` in the prelude log line at the same second as the take. A real pool's
prelude reports `repos=60`; `repos=2` is that test's two-repo fixture `relay.toml`.

A second misleading surface, found the same way: an isolated `INJECT_BASE` still appended to the
SHARED `~/.claude/logs/relay-inject.log`, so the canary probes run while diagnosing this wrote
three `take scope=<global> consumed=1` lines that read as takes against the live queue.
`INJECT_LOG` is now isolated too, in both test files.

## How long it had been happening

Not new. The `repos=2` fixture signature appears in `~/.claude/logs/discover-prelude.log` on
every suite-running day back to at least **2026-08-26** (130 prelude emissions that day alone).
It became visible on 2026-09-10 only because the queue happened to be non-empty when it fired --
the first `[MECHANICAL]` batch had just injected 19 review units overnight. Every earlier drain
took whatever was pending, silently. There is no way to enumerate what was lost before today:
`inject.done/` records the shards but not whether a pool ever saw them.

## The fix

1. `tests/test_prelude_mechanized_86a2.sh` now isolates `INJECT_BASE`, `CLAIM_BASE`, `STOP_PATH`,
   `RELAY_DISCOVER_PRELUDE_LOG` and `INJECT_LOG`. Still green.
2. New `tests/test_inject_queue_test_hermeticity.sh` plants a canary unit and asserts every
   prelude/inject-executing test leaves it untouched. The candidate set is **derived** from
   execution shape, so a future test is covered automatically -- the point, since this leak
   arrived with a test nobody thought to check. ~2.3s.

**Deliberately NOT a static lint.** The obvious rule -- "a test referencing `discover-prelude.sh`
/ `inject.sh` must set `INJECT_BASE`" -- was tried first and is wrong: nine test files match that
shape and only ONE leaked; the other eight are hermetic by other means. A guard that is wrong
eight times out of nine gets muted, which is how the leak would survive its own fix. The canary
MEASURES the property instead of inferring it.

## Recovery

`code.lawless` restored its 18 shards from `inject.done/` to `inject.d/` and consumed them in a
`--relay --afk --only code.lawless` run at 07:47:59. This session restored the `ai-codebench`
`0ce2` shard. `routed:a923`'s `take --repo` scoping is what kept the out-of-scope shard pending
through their run, as designed.

## Standing gap, not duplicated here

A consumed-but-never-dispatched injection is invisible and unrecoverable -- that is `id:f3a0`,
which stands unchanged. `routed:a923` (scope violation at the consuming layer) also stands. This
item is the non-hermetic test, nothing more; do not fold the queue-durability question into it.
