The cause is a real limit
of static extraction, not a bug: it cannot tell WHICH regex inside a reader file is applied to
ledger text, so every regex in a file that also happens to read a ledger counts as a search
over the ledger. Some are genuine, e.g. `tracker/ledger-map.py`'s
`\*\*(Acceptance|Tests|Done-check|Context)\*\*`. Many plainly are not, e.g.
`tools/ledger-continuations.py:283`'s `\$[A-Za-z_{(0-9]`.

Refusing is the SAFE direction, and our live ledgers hold zero continuation blocks, so this
costs this repo nothing today. It is not free elsewhere: a peer repo's shrink run is gated on
this tool and its corpus is full of blocks.

### The second defect, which is the worse one

**Union-anchoring is FILE-level, so a file that reads notes in one function and the ledger
alone in another is a FALSE CLEAR.** Demonstrated while running `9ce0`'s done-check: reverting
`roadmap-lint.sh`'s heredoc parser alone did NOT flip the verdict, because the same file still
reads notes at `:368` and `:1132`. All three reads had to be neutered before the refusal fired.

This one fails in the WRONG direction. The 105-site over-refusal is loud and safe; this is
silent and unsafe, and it is the same missing analysis. That asymmetry is why the owner chose
this option over the cheaper high-confidence/possible split.

**On 2026-09-01 this exact failure cost four id markers.** `89f9`, `a5b6`, `ba07` and `ed26`

So the asymmetry above is not a thought experiment: the loud over-refusal costs a human pass,

### THE INSTRUMENT IS ALSO A SUBJECT -- handle it deliberately

The shrink tool itself is a both-reader, in BOTH repos. loderite's `extract-roadmap-notes.mjs`
performs the relocation AND lands in the reader set being analysed; ours does the same, and
`tools/ledger-continuations.py` is already the single largest UNANALYSABLE contributor on our
tree (63 constructs) precisely because it names ledger basenames and is dense with regexes.

A file-level union resolves that self-reference arbitrarily, in one direction, with nothing
recording which. **Decide it rather than fall into it**: either the narrowing handles the
instrument as a construct-level case like any other, or the instrument is a NAMED exclusion
with a written reason. A silent arbitrary resolution is not an acceptable third answer.

### What to build

Construct-to-corpus dataflow: track which pattern is applied to text actually READ FROM a
ledger, at CONSTRUCT level rather than file level.

- A pattern counts as a ledger search only when its subject traces back to a ledger read.
- Union-anchoring resolves per construct, so one function reading notes no longer clears a
  sibling function that reads the ledger alone.
- The rejected cheaper option, recorded so it is not silently revived: naming a SHORT
  high-confidence set beside the long possible set. It needs no dataflow, but the boundary is
  a heuristic, and anyone treating the short list as THE list has rebuilt `id:cb3e` in a new
  costume.

Everything `9ce0` established is a floor and must survive: no id-keyed or token-keyed list
(its test (F) asserts this), one-level constant fold before UNANALYSABLE, UNANALYSABLE reports
its assignment site, strip-then-match followed rather than short-circuited at the anchor,
basename-composed path matching, and the self-test that makes the counter able to fail.

**No per-repo or per-grammar branches.** If the narrowing needs one, it is wrong. The
predicate answers "is this token the item's OWN marker", which is a grammar question whose
answer differs per repo, and it must arrive at that by following data, never by assuming a
shape.

- **Acceptance**: a refusal's named consumer set contains only patterns whose subject traces
  to a ledger read; the `roadmap-lint.sh` false clear fires when its heredoc parser alone is
  reverted, without neutering its notes reads; the instrument-as-subject case is resolved
  explicitly (construct-level, or a named exclusion carrying a written reason); and every
  `9ce0` floor property above still holds, its self-test included.
