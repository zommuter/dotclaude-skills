## The gate charges for the exact thing the trimming exists to prevent

`id:0d7c`'s line-shrink relocates item prose out of `TODO.md`/`ROADMAP.md` into
`docs/ledger-notes/<id>.md`. **Its purpose is that the complete notes never enter any
context** (owner, 2026-09-09): a child follows the ONE pointer for the item it is working and
nothing else. The corpus is deliberately addressable-but-unloaded.

The prompt-size gate's whole-ledger path does the opposite. `classify-repo.sh:230` computes

    roadmap_bytes = os.path.getsize(rm) + _ledger_note_bytes(rm)

and `_ledger_note_bytes` walks EVERY `docs/ledger-notes/…` pointer in the file and sums those
files' sizes (`id:b018` does the same for the second ledger). Measured on this repo,
2026-09-09:

| input                          | bytes     | share |
|--------------------------------|-----------|-------|
| `ROADMAP.md` itself            |    37,337 |  1.5% |
| `TODO.md` itself               |   225,985 |  9.4% |
| notes behind 714 unique pointers | 2,150,693 | 89.1% |
| **total**                      | **2,414,015** (~603,503 tok) | |

The notes directory is 2,405,763 B across 845 files, so the gate is charging essentially the
entire corpus -- **89% of the estimate is bytes the architecture guarantees will never be in
one context at once.** The ledgers themselves are 11%.

## Why `id:f3d2` is right where it was aimed and wrong here

`id:f3d2` added pointer-counting because the gate "must count pointed-to files or it goes
optimistic". That is correct for the SLICED path: a sliced child DOES follow its own item's
detail pointer, so the slice's true cost includes that one note, and under-counting it
disarms the guard. Applied to the WHOLE-LEDGER path the same rule models a child that reads
all 714 notes, which no child does and which `id:0d7c` exists to make impossible.

Same rule, two paths, one of which it does not fit.

## The consequence, not hypothetical

Run `relay-20260909-185356-12943` refused every execute dispatch at ~668,626 tok against a
100,000 budget, twice, producing `repeatHandbackKind: bug-signal` and
`stopReason: blocked-pending-human`. The unit reached the whole-ledger path because it was
unnamed and therefore unsliced (`id:7f4c` -- the separate defect that got it there). Whatever
fixes `7f4c`, this estimate stays wrong for any future unsliced unit.

**And it makes the shrink look useless against its own motivation.** Relocating a line's prose
into a note moves the bytes from the ledger file into a counted note, so the whole-ledger
estimate is roughly conserved (notes are summed once each -- `sorted(set(...))` -- so this is
not double-counting, merely non-reduction). A reader measuring the shrink by this gate would
conclude the programme achieves nothing, when in fact it achieves exactly what it was for:
the notes are no longer in the child's context. The gate is measuring a quantity the design
already decoupled from real context cost.

**Acceptance**: the whole-ledger estimate stops charging the full pointed-to corpus. State
the replacement explicitly rather than deleting the charge: a BOUNDED allowance (the pattern
`RELAY_LOG_WINDOW_BYTES` already sets for `RELAY_LOG.md` on review units, where a census found
whole-file reads at ~3%) is the closest existing precedent -- charge N notes' worth, not 714.
The sliced path keeps counting its own item's note unchanged: `id:f3d2`'s reason holds there
and must not be regressed.

**Done-check**: a hermetic test with a fixture ledger carrying many note pointers, asserting
the whole-ledger estimate does NOT scale with pointer count beyond the bound, AND a second
fixture asserting a sliced unit still includes its own note's bytes (so the fix cannot be
"stop counting notes"). Re-measure this repo afterwards and record the new figure in this
note. `make test` green.

**Context**: `relay/scripts/classify-repo.sh:195-230` (`_ledger_note_bytes`, `roadmap_bytes`,
the `id:b018` second ledger), `relay/scripts/prompt-size-gate.mjs` + its inline copy at

## Open question this note does not settle

Whether the bound should be a fixed N, a fraction of budget, or "the notes reachable from the
items a child may actually work". The third is the most faithful to reality and the most work;
the first is a one-line change. That is a cost/fidelity call, not a fact, so it is left for
the owner or a handoff to decide rather than assumed here.
