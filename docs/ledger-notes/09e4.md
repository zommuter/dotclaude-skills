## From TODO

— `_mechanical_dispatch` admits a `relay-mech-stdin` fence whenever `_last_stage_relay_script(command)` (the LAST pipeline stage's pinned script) is in `STDIN_ALLOWED_SCRIPTS`, but `_run_mechanical` feeds the payload via `subprocess.run([bash,'-c',command], input=stdin)` — which reaches the SHELL process's stdin, i.e. the FIRST stage of a pipeline, not the last. So a command like `echo x | relay-status-publish.sh` (both `echo` and the admitted script pass `_command_allowed`) with a stdin fence would send the payload to `echo` (which ignores it) while the admitted script reads the pipe (`x`), NOT the payload — a silent wrong-bytes delivery. **NOT an active vuln / LOW**: the command is caller-constructed by `relay-loop.js` (trusted) and the only admitted member (`relay-status-publish.sh`) is invoked bare, never piped; nothing dangerous runs and no data leaks — the payload is merely lost. But it is LATENT: the design intent is documented as "the command stays a single bare allowlisted script invocation", and the gate does not enforce that shape, so the moment an admitted script is used downstream of a pipe its stdin silently receives the wrong bytes. **Fix**: when a `relay-mech-stdin` fence is present, require the command to be a SINGLE stage (no unquoted `|`) — refuse (fail open, log `mechanical_stdin_refused` with reason `stdin fence on a multi-stage pipeline`) otherwise; a bare admitted invocation is the only shape that delivers stdin correctly. RED test: a `relay-mech-stdin` fence on `echo x | relay-status-publish.sh` (admitted last stage) → `_mechanical_dispatch` returns None; the bare-invocation case stays green.
