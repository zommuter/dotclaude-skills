**SECOND SURFACE -- CORRECTED 2026-09-08, same session. This note's original claim was
WRONG and is retracted here.** (Declared per the notes-are-editable rule in
`docs/ledger-notes/README.md`: this note has been edited since authoring.)

The original text read: *"`~/.config/relay/relay-events.jsonl` contains **zero**
`"kind":"dispatch"` rows for this run ... it is specifically the dispatch event that never
lands."* That was a true MEASUREMENT and a false INFERENCE. The row does exist:

```
{"ts":"2026-09-08T15:45:01Z","runId":"relay-20260908-174448-4421","kind":"dispatch",
 "repo":"trustless-ai","mode":"execute","tier":"sonnet","round":1,"item":"fa13", ...}
```

Its `ts` is the dispatch instant, but it was not in the file when grepped several minutes
later -- it was appended afterwards, backdated. That is the documented off-critical-path
flush (`id:c8b6`: events are "flushed off-critical-path via `relay-state-write.sh
event-append`"). So the defect on this surface is **flush LATENCY, not event loss**, and
"never lands" was an unwarranted jump from one observation to a permanent property. The
operator-visible symptom was real -- at the moment of looking, the live unit appeared
nowhere -- but the event feed self-heals and a fix aimed at "the dispatch event is not
written" would have chased a bug that does not exist.

**What survives, and is stronger than first stated: the `RELAY_STATUS.md` half.** That does
not self-heal, and its scope is wider than the single unit this note was opened on. Measured
again at round 6 of the same run:

> INCOMPLETE ACCOUNTING (id:8c85) -- **12 of 59** reached NO section -- claude-organizer,
> collaib, inflownistration, zkm-calendar, zkm-claude-ai, zkm-claude-code, zkm-eml,
> zkm-notmuch, zkm-photo, zkm-social, zkm-stt, zkm-vcard.

The membership CHANGES between rounds (round 1 named only trustless-ai; round 6 names twelve
different repos, none of them trustless-ai), so this is not one stuck row -- the
section-assignment is unstable across rounds. That instability is the real finding.

**Why the previously banked framing is incomplete.** The `relay-status-accounting-temporality`
memory records `id:8c85`'s falsification as a SCOPE issue -- mixed-temporality sections, and
"every repo in exactly one section" being false on round 2 of any run, with `--only` as the
trigger. This instance is round **1** of a plain fleet-scope run with no `--only`, and the
missing member is the in-flight unit rather than an accumulated one. So the temporality
correction does not cover this case, and the remaining defect is not merely presentational:
the operator's only two machine-readable views of a live run both omit the single thing the
run was doing.

**Severity is the ordering, not the count.** One missing row out of 59 sounds minor. The
missing row was the ONLY dispatched unit, so the file's error rate on the question the
operator actually asks -- "what is this run doing right now?" -- was 100%.
