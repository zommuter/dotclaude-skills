## From TODO.md

**The defect.** `relay/scripts/todo-conformance.sh --inbox <inbox>` reports EVERY open
inbox line as `shape-prose`. The id:30fe structural shape check is the ONLY per-line rule
in that script with no `inbox -eq 0` guard:

| Rule | Guard site | Skips `--inbox`? |
|---|---|---|
| b048 ledger-line grammar | `:1152`, `:1206` | yes |
| id:0d7c head-length ratchet | `:1166` (`LENGTH_RATCHET_ON`) | yes |
| id:2d17 shape ratchet baseline | `:1166` (`SHAPE_RATCHET_ON`) | yes |
| decided-left-open (id:cb3e) | `:1250` | yes |
| baseline-staleness mode | `:1034` | yes |
| **id:30fe `shape_class`** | **`:1267` -- none** | **NO** |

The script's own header states the intended scope for this family: *"Out of scope, same as
the ratchet: `--inbox` and `*.archive.md`"*. `shape_class` does not honour it.

**Measured 2026-09-10** on the live store `~/.claude/projects/todo-inbox.md` (3 open items,
all three structurally conforming -- `classify_inbox` returns clean and the run exits 0):

```
shape-prose (592 chars of prose outside lane/gate/id/title/pointer; id:30fe)	536	- [ ] [cartulary] ...
shape-prose (168 chars of prose outside lane/gate/id/title/pointer; id:30fe)	551	- [ ] [meeting-rpg] ...
shape-prose (227 chars of prose outside lane/gate/id/title/pointer; id:30fe)	627	- [ ] [leAIrn2learn] ...

```

3 of 3 -- so the rule carries zero information on this path. The three lines are also
`id:798d`-legal: an `<!-- id|routed:XXXX -->` marker followed by (or preceded by) trailing
prose is EXPLICITLY legal shape, which is what `id:798d` established for the ledger and
what `docs/ledger-notes/0246.md:51` and `db8c.md:41` both restate.

**Why it matters beyond noise.** The collision is visible in output: one
`scan-routed.sh --apply` run printed the SAME line as both non-conforming and `RESOLVED`
(recorded in `docs/session-handover-2026-09-10.md:145-147`). A reader cannot tell which
verdict to act on.

**Severity bound, stated so it is not over-sold.** This is REPORT-ONLY on the inbox path
and cannot escalate: `SHAPE_RATCHET_ON` is set only inside the `inbox -eq 0` block
(`:1179`), so on `--inbox` `shape_class` always takes the `SHAPE_RATCHET_ON == 0` branch
(`:601`) and emits `shape-prose`, which is never added to `strict_findings` (`:1314`). The
escalating classes `shape-new` / `shape-regrowth` are structurally unreachable here.
`--strict` therefore cannot be failed by this. The cost is a saturated, uninformative
finding class on a path that already has a competing verdict printed beside it.

## The three other live opinions about inbox line shape

This is the FOURTH. The other three are enumerated by `id:0246` (`TODO.md:208`), which is
OPEN and whose implementation was REVERTED 2026-09-10 (`eb2587fd`):

1. **`scan-routed.sh` -- FIRST marker on the line** owns the item.
2. **`append.sh add` -- LAST marker on the line** owns the item.
3. **`append.sh inbox-done` -- END-OF-LINE marker only** owns the item, so an
   `id:798d` trailing-prose line is owned by NO token.

`id:0246` records the owner's 2026-09-10 ruling that a multi-marker line must be REFUSED
rather than guessed. **a715 is a different axis and does not re-open that ruling**: 0246 is
about which token OWNS a line (a destructive-write question), a715 is about whether the
line's PROSE SHAPE is a finding at all (a report-only question). They touch the same three
live lines, which is why the two verdicts appeared together.
