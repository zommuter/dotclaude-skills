### What was corrected

`routed:de13` reported that `pnpm <script>` cannot run inside a relay worktree. It can. The
blocker is pnpm's pre-run deps-status check, not the worktree layout.

### The lever

```
export PNPM_CONFIG_VERIFY_DEPS_BEFORE_RUN=false
```

This disables the pre-run deps-status check and **authorises no removal**, which is what
distinguishes it from `CI=true` / `confirmModulesPurge=false` -- those purge the MAIN
checkout's `node_modules` through the worktree symlink (`id:b115` holds that refusal).

### Measured, not assumed

Verified in zkWhale on 2026-09-07: `pnpm typecheck`, `lint`, `test`, `test:zk` and `test:e2e`
all ran GREEN inside the relay worktree, and the symlink was byte-identical afterwards.

### The proposal

Set `PNPM_CONFIG_VERIFY_DEPS_BEFORE_RUN=false` in the relay child environment so pnpm repos
stop reading as red across the fleet. That is a change to this repo's relay child env, which
is why the item lands here rather than in zkWhale.

- **Acceptance**: a relay child dispatched into a pnpm repo can run the repo's test scripts
  without `ERR_PNPM_ABORTED_REMOVE_MODULES_DIR_NO_TTY`, and no pnpm invocation on that path is
  authorised to remove a modules directory.

- **Done-check**: the env var is set where the relay child env is composed, with a test
  pinning both halves -- the var present, and neither `CI=true` nor `confirmModulesPurge`
  set.
