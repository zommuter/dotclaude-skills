## From TODO

**The `id:1432` repeat-handback ALERT keys on repo+verdict, so it cannot express the signal
it exists to catch: the same ITEM being refused over and over.** Measured in run
`relay-20260908-174448-4421`, 2026-09-08.

The alert did fire -- three times (dotclaude-skills 4, wisenheimer 4, loderite 3) -- so this
is not a silent-no-op. It is a GRANULARITY defect: the alert says "wisenheimer handed back 4
times", which reads as a busy repo. What actually happened is sharper and is a bug signal:

> **wisenheimer refused the SAME SIX ids in all three of its substantive handbacks** --
> `c071`, `cd03`, `6f17`, `8750`, `9b11`, `eae0`, at 17:04, 17:14 and 17:48.

That is three dispatch slots spent re-deriving the identical refusal set. A repo+verdict
counter cannot distinguish it from three handbacks on three different items, which would be
ordinary progress through a hard backlog.

**Why item granularity is the right key.** The `id:1432` gloss calls a repeat handback "a
bug signal", and the thing that makes it a bug signal is *repetition on the same work*, not
volume. A repo that hands back four different items is working; a repo that hands back the
same six ids three times is looping, and every extra round is pure waste -- the classifier
re-selects them, a child re-reads them, and the refusal is re-derived unchanged.

**What to build.** Key the alert on `(repo, item-id)` and alert when the same id is refused
in N>=2 rounds of one run. The data is already present: the per-item ids are recoverable
from the handback event reasons, which is how the six above were derived. No new collection
is needed, only a different key.

**Do NOT read this as "the alert is broken".** It reported exactly what it measures. The gap
is between what it measures and what an operator needs to see, so the fix is additive -- a
second, finer alert -- not a replacement of the existing counter.
