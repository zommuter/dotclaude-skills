## From TODO

`md-merge.py update-ids`'s `regex_sub` op is a **SILENT NO-OP when the id IS found but the
pattern does not match that line**. Found 2026-09-04 (kienzler-solutions, editing item
`id:9f11`). The unmatched guard at `meeting/md-merge.py:494` computes `regex_sub_ids - found`,
i.e. it only fires for an id that does not exist at all; a found id whose pattern misses
simply writes the file back unchanged and exits 0. The caller gets no signal and, in that
case, believed the ledger had been updated for a full turn.

Same class as the no-silent-swallow ban (`id:4347`) and the sibling append defect (`id:e166`):
a helper whose *detection* half works and whose *resolution* half quietly does nothing.

The `append` op has the same shape and is in scope for the same pass.

### Measured, not inferred (2026-09-05, relay handoff)

Against `meeting/md-merge.py` at `9d5048a62acbacbd3a918212341606a01dd25cae`, on a fixture
holding `- [ ] **An item** with stale prose here <!-- id:aaaa -->`:

| payload | exit | file |
|---|---|---|
| `{"regex_sub":{"pattern":"NOTHING_MATCHES_THIS","repl":"x"}}` | 0 | unchanged |
| `{"regex_sub":{"pattern":"stale prose","repl":"fresh prose"}}` | 0 | changed (correct) |
| `{"append":""}` | 0 | unchanged |
| `{"append":"   "}` | 0 | unchanged |
| `{"append":"-- AMENDED."}` | 0 | changed (correct) |
| `{"regex_sub":…}` on an id NOT in the file | 1 | unchanged (correct, `id:f26d`) |

So both no-op shapes are real and both are silent. The `append` shape comes from
`_append_to_line` (`:304-313`), which does `text = append_text.strip()` and then
`body = f'{prefix} {text}' if text else prefix` -- a whitespace-only or empty payload
reconstructs the original line and the caller is told nothing.

### Why the obvious fix is not enough

Comparing the FINAL composed line against the ORIGINAL line does not catch it. Since `id:5d7e`
the ops for one id are FOLDED in payload order, so a delta of two ops where the first hits and
the second misses leaves the line changed overall -- and a whole-line comparison reports
success while half the caller's intent was dropped. That is the same "one bucket wins, exit 0"
shape `id:5d7e` itself existed to close.

The tracking therefore has to be **per op**, which is exactly what the TODO's FIX text says.

### What to build

Track, per op, whether the op actually changed the composed text. When a `regex_sub` matched
its id but produced no change, or an `append` resolved to appending nothing, fail LOUDLY:
non-zero exit, write NOTHING, and name **both the id and the offending pattern/op** on stderr,
in the same `errors`-list style the file already uses for `id:0af4` / `id:1b1a` / `id:f26d`.

A DELIBERATE no-op opts in through an explicit flag rather than being the default. The spec
pins the flag as `--allow-noop`; the name is a judgment call, recorded in `REVIEW_ME.md`.

- **Acceptance**: a `regex_sub` whose id is found but whose pattern does not match exits
  non-zero, writes nothing, and names the id and the pattern on stderr; the same holds for an
  `append` whose payload is empty or whitespace-only; a folded delta in which one op hits and
  another misses ALSO fails and writes nothing; `--allow-noop` makes such a delta succeed with
  the file unchanged; and every existing hitting-op / unmatched-id / `--allow-new` behaviour is
  unchanged.

- **Done-check**: `tests/run-tests.sh tests/test_md_merge_silent_noop_3bd4.sh` is green, then
  `make test` is fully green.
