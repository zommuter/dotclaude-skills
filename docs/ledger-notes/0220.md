## From TODO

**Origin.** Owner question 2026-09-08: given `[MECHANICAL]`'s open points, should a relay
`--intensive` pool also spawn `[MECHANICAL]` tasks in adequate isolation, dispatched through
the `bash` proxy model?

**The proposal as literally stated is REFUTED on three verified grounds.** Recorded here so
nobody re-derives it:

1. **The proxy confers no classifier protection.** `id:e62c` ran the discriminating
   experiment on 2026-07-29 (run `relay-20260729-111723-7520`, `wf_27347d26-007`) with the
   proxy VERIFIED in path (`probe-mech-proxy.sh discriminate` -> healthy,
   `mech-preflight.sh preflight` -> proceed, so no Haiku fallback was in effect). A hop
   hardcoded `model:'bash'` at `relay-loop.js:2316` was STILL blocked by the safety
   classifier. Conclusion recorded there: the classifier sits at the `agent()` DISPATCH
   layer, upstream of where `mechanical-proxy.py` intercepts at the HTTP layer. So the most
   attractive motive for the proposal -- dissolving the classifier-tax class (`id:83c2`,
   `id:51f0`, `id:1ed3`) -- does not materialise. The mechanism shown to work for that class
   is the FRONT DOOR (`id:54be`), which is not an `agent()` dispatch at all.
2. **Duration shape.** The proxy short-circuits ONE synchronous HTTP turn;
   `MECH_PROXY_TIMEOUT` defaults to 120 s. The motivating `[MECHANICAL] [INTENSIVE]` class
   has `est_wall` 4500-5400 s (`id:c057`). A pool round would block on an `agent()` call for
   hours, and `id:6d01` (restarting `mechanical-proxy.py` silently kills in-flight agents in
   OTHER live sessions) would grow from a 30-second blast radius to an hours-long one. The
   daemon is immune to proxy restarts today.
3. **Isolation runs the wrong way.** `mechanical-proxy.py`'s own header states it "adds no
   sandbox of its own" and runs the subprocess with the driver's privileges. The containment
   already lives on the DAEMON side: `capped-run.sh` (cgroup MemoryMax, no-swap, own
   `relay-mech.slice`, fails closed), `RELAY_REQUIRE_SERVICE_USER`, host gate, intensity +
   resource gate, repo-lease peek-and-defer, whitelisted-recipe validation. Routing through
   the proxy means rebuilding all of it. Note also `id:c057`'s same-day scope correction and
   `id:3770`: even the daemon's cap does not reach `resource: local-llm`, because
   `llama-swap` loads the model in its own root cgroup.

**It would also amend a RATIFIED decision.** `relay/references/hard-lanes.md` (meeting
`2026-07-02-1924` D1) fixes `[MECHANICAL]` as pool-inert, run by a host daemon; the `id:2313`
branch routes compute-only work to `[MECHANICAL]` "daemon-run, not pool-dispatched". Any move
in this direction is the owner's call, not a session's.

**What SURVIVES, and is the actual item: move the TRIGGER, not the executor.** The proposal's
kernel is right that there are TWO schedulers. The pool has the `--intensive` gate plus the
`resource:` claim; `mechanical-daemon.sh` re-implements a launch gate
(`relay-intensity.sh permits` + `resource-probe.sh` + `claim.sh peek`). The rest of the loop
is already closed: handoff C2 (`id:9c88`) produces recipes, the daemon consumes them, and
`inject.sh` returns the artifact for pool review.

So: let an `--intensive` pool round DROP the recipe and then TICK the daemon, with ONE shared
`claim.sh acquire` spanning both. That lands directly on two already-open `id:1cb8`
sub-points, which is why this is a composition item rather than a new substrate:

- `id:1cb8` defect (2) -- the only trigger is edge-based (`mechanical-daemon.path`
  PathModified on `pending/`), so a DEFERRED recipe stalls until an unrelated write. A
  pool-driven tick is a second, purposeful trigger.
- `id:1cb8` defect (5) -- the daemon only PROBES the resource claim, never ACQUIRES it, so a
  recipe and a concurrent pool job can both see "free" and launch on one GPU. One shared
  acquire is the fix on both sides.

**Design question left for the owner:** whether the pool-driven tick is a direct
`mechanical-daemon.sh tick` invocation from the front door (not an `agent()` dispatch, so
outside the classifier's reach, matching the `id:e62c` finding) or a `.timer` companion the
pool merely nudges. The `.timer` companion is itself an open `id:1cb8` sub-point, so the two
should be decided together rather than built twice.

**Short-duration mechanical work is NOT in scope here.** In-Workflow `model:'bash'` already
IS the mechanism for that class (`MECH_MODEL` at `relay-loop.js:137`; both discovery hops run
that way). The split point is duration and containment, not lane.
