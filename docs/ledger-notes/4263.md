## From TODO

**`relay-reconcile.sh --integrate` PUBLISHES to a public remote automatically, which
`id:f66e` forbids.** Observed 2026-09-08 integrating a parked orphan in this repo.

**The evidence.** The integrate recipe's push step is
`git-lock-push.sh --ff-only --all` -- documented that way in `relay/SKILL.md`'s Reconcile
mode, and it does what it says:

```
To https://github.com/zommuter/dotclaude-skills.git
   f6fa91d1..8aecd0f1  main -> main
 * [new tag]           relay-ckpt-20260908-1754 -> relay-ckpt-20260908-1754
privacy-gate: remote 'origin' (fievel:src/dotclaude-skills.git) is a PRIVATE host — skipping leak scan.
```

One operator action (`--integrate <branch>`) pushed to public GitHub with no prompt, no
confirmation, and no mention of publishing in the command's name or its output beyond the
push line itself.

**Why this is a contract violation, not a preference.** `id:f66e` (owner decision
2026-08-22) states publishing to a PUBLIC remote is never automatic. `git-lock-push.sh`'s
own default was narrowed to `origin` ONLY on 2026-08-26 for exactly this reason -- its prior
"push every remote" default is described in `git-diary-workflow/SKILL.md` as "the footgun
this skill's `--remote origin` requirement used to guard against". The reconcile path keeps
that footgun by passing `--all` explicitly, so the 2026-08-26 narrowing does not reach it.

**`integrate.sh` already solved this; reconcile never got the fix.** `id:4d44` gave the pool
integrator per-remote push narrowing via `relay/scripts/lib-private-remote.sh` -- THE single
"is this remote a PRIVATE/LAN host?" predicate -- plus the `ratification_pending` queue, so a
public-remote push is WITHHELD and surfaced for a human to review and push. The reconcile
path calls neither. Two integration paths, one contract, one implementation. This is the
same shape as the bank memory `bump-changelog-reaches-one-of-three-paths`: a rule
implemented on the path its author was looking at.

**DIRECT A/B EVIDENCE, same repo, same day (added 2026-09-08; this note has been edited
since authoring, per `docs/ledger-notes/README.md`).** The running pool integrated
`dotclaude-skills` five times while this note was open, and every one of those integrates
WITHHELD the public remote and queued it:

```
$ ratify-queue.sh list --tsv | grep -c pending
5
dotclaude-skills  ratification_pending  [RATIFY id:4d44] pool merged LOCALLY and pushed
  only the PRIVATE/LAN remote(s); [github] still need an owner push: ...
  (ckpt=relay-ckpt-20260908-1804 ids=4f0f ...)
```

`RELAY_STATUS.md` records those integrates as `push=partial`, versus `push=pushed` for repos
with no public remote. So on the SAME repository, on the SAME day: the pool integrator
correctly withheld GitHub five times and asked for an owner push, while
`relay-reconcile.sh --integrate` published to GitHub once, unprompted. This is no longer an
inference from reading the code -- it is an observed A/B between the two paths, and it
settles that the contract is implemented on one and absent on the other.

**Blast radius.** Fourteen of 56 own repos carry a public GitHub remote (re-measured
2026-08-27): `dotclaude-skills`, `zkm`, `toesnail`, `proton-moresync`, and ten zkm plugins.
`relay-reconcile` is a HUMAN-invoked mode, run precisely when someone is disposing of parked
work they have not necessarily read -- an orphan is by definition a `id:f272` "WIP UNVERIFIED
residue" commit. Publishing unreviewed residue is the worst possible default for that verb.

**The privacy gate is not the backstop.** It ran on the public push and logged one hit, but
it is warn-only (`exit 0`, never blocks) and DIFF-scoped, exactly as `id:9bfc` records. It
observed the publish; it could not prevent it. The hit itself was a false positive -- a short
private pattern matching inside an ordinary English word -- which is beside the point.

**Suggested fix.** Route the reconcile push through `lib-private-remote.sh` the way
`integrate.sh` does, so a public remote is withheld and queued via `ratify-queue.sh` rather
than pushed. Do NOT substitute `git-lock-push.sh`'s `is_ssh_url()`: `CLAUDE.md` records that
it is an SSH-AUTH predicate and "fails toward auto-publish", which is the wrong direction
here. A done-check should assert that `--integrate` in a repo with a declared public remote
advances the private remote, leaves the public one unadvanced, and records the withholding.

## ESCALATION 2026-09-08 -- the gap does not merely bypass the policy, it ERASES THE RECORD of it

(This note has been edited since authoring, per `docs/ledger-notes/README.md`.)

Third occurrence tonight, and this one had a second-order effect nobody predicted.

Integrating the parked `...execute-5ad9-0` orphan via `relay-reconcile.sh --integrate`
pushed `main` to the PUBLIC GitHub remote unprompted, as before -- `git ls-remote github
refs/heads/main` now returns `24097ad22b93`, identical to local `HEAD`. But because
`ratify-queue.sh` SELF-VERIFIES landing via `git ls-remote`, that unprompted push made all
**six** `ratification_pending` entries verify as landed:

```
before: ratify-queue.sh list --tsv | grep -c pending  ->  6
after :                                               ->  0
```

**So the queue whose entire purpose is to hold a public push for an owner decision was
drained BY the unreviewed public push.** The six entries (ckpts 1804, 1835, 1934, 1947,
2042, 2052) did not get reviewed and released; they got overtaken. Nothing is left to show
that an owner decision was ever outstanding -- the evidence self-erased, and a later reader
sees a clean queue and concludes the policy was honoured.

That is materially worse than "one path forgets to narrow the remote". A bypass that leaves
its own audit trail intact is recoverable; one that satisfies the audit as a side effect of
bypassing it is not. It also means the count in the section above -- "the pool withheld
GitHub 5x while one reconcile published once" -- can no longer be reproduced from the queue,
only from this note and the run's checkpoints.

**Sharpens the fix.** Narrowing the reconcile push per-remote (the `lib-private-remote.sh` +
`ratify-queue.sh` route `integrate.sh` already uses) is still the change. But the done-check
must now also assert the NEGATIVE: after a reconcile integrate in a repo with a declared
public remote, any pre-existing `ratification_pending` entries are STILL pending. A test that
only checks "the public remote did not advance" would pass on a build that advanced it and
then silently resolved the queue.

**Irony worth recording, not for its own sake but because it dates the exposure:** the commit
this reconcile published is `id:7408` seam 1 -- the change that makes `integrate.sh` withhold
a public remote while any unresolved queue entry is ancestral to HEAD. The fix for one path
reached the public remote through the unfixed path, and cleared the queue on the way.
