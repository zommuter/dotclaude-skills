# id:5a56 -- `verify-isolation.sh` has a false-positive FAMILY; reframe the predicate

Filed 2026-09-10. Covers `id:01dc` (inbound `routed:9102` from escapement) and the third,
previously unfiled wrinkle recorded below. `id:3016` is the already-fixed first instance and is
kept here as evidence, not as work.

## The three instances, and what they have in common

| # | instance | status |
|---|---|---|
| a | git-annex pointer noise read as DIRTY -- every annex worktree, so units handed back on EVERY round on `code.lawless`/`zkWhale` | FIXED 2026-09-09 (`53d43bcd`) |
| b | the `id:88f0` ledger-only exclusion omits the ARCHIVE files, so a routine archive commit reads as an isolation breach (`id:01dc`) | OPEN |
| c | `status --porcelain` read 0 while `git worktree remove` still judged the tree dirty | OPEN, unfiled until now |

The gate's predicate is **"any signal means unsafe"**. Every one of the three is a signal that
does not mean unsafe. Each was found separately, by a different repo hitting it, and each was
patched (or would be patched) as its own special case. That is the thing to stop.

## Why a reframe rather than a fourth patch

Three instances in three weeks, from three unrelated repos, is a rate -- and each patch narrows
the predicate by one hand-written exception while leaving the predicate's SHAPE untouched, so
the next repo with a different benign signal reproduces the bug. The work here is to decide what
the gate is actually asserting and express THAT, rather than to enumerate benign signals until
they run out (they will not).

Worth noting what makes a reframe safe to attempt: instance (a)'s fix was deliberately narrow
-- clean only when every entry is the exact ` M` pair AND `git diff --quiet` passes, so
untracked still reads dirty, which is most of what the gate exists to catch. A reframe must keep
that property. The risk direction is asymmetric and should be stated in whatever replaces the
predicate: a false POSITIVE costs a handback per round, a false NEGATIVE lets a child's work
escape its worktree (`id:c6c8`), which is the failure the gate exists for.

## A caution specific to instance (c)

(c) is the one that says the predicate is reading the wrong ORACLE, not merely reading it too
strictly: two git commands disagreed about the same tree. Resolve (c) before designing the
replacement, because if `status --porcelain` is not authoritative for "would `worktree remove`
succeed", then the replacement predicate cannot be built on it either. Do not assume (c) is a
stale-index artifact without establishing it -- that is a claim about code behaviour and wants
the command that proves it.
