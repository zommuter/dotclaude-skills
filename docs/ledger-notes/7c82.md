Authored directly (not relocated by `tools/ledger-shrink.py`).

## From TODO

Found by the independent review of `id:60eb`, 2026-09-03. **This is a standing hole affecting
every closed roadmap-spec test in the repo, not one file.**

### The defect

`tests/verify-negative-cases.py:640` searches the WHOLE FILE for `# roadmap:XXXX` and buckets
the file as `roadmap-spec (skipped: redness IS the spec)` **before any `# fails-against-*`
declaration is considered**. A file carrying both gets:

```
ROADMAP-SHADOWED DECLARATION -- 1 file(s) ... the roadmap carve-out cancels
the declaration and they are NOT verified
```

So `# roadmap:` and `# fails-against-mutation:` are MUTUALLY EXCLUSIVE, and the declaration
is reported as shadowed rather than run.

### Why it is worse than a one-off

**The carve-out never expires.** It keys purely on the PRESENCE of the token:
`grep -n "ROADMAP.md\|checkbox\|\[x\]" tests/verify-negative-cases.py` returns NOTHING, so it
never consults the item's checkbox.

The carve-out's own justification is the EXPECTED-RED rule -- a red test IS the spec while its
roadmap item is OPEN. But once the item is TICKED, `tests/run-tests.sh` stops granting
EXPECTED-RED (correctly -- that is the definition-of-done check), while
`verify-negative-cases.py` goes on cancelling the file's declaration forever. The two runners
disagree about what `# roadmap:` means, and the disagreement is silent.

Every closed roadmap-spec test in the repo is therefore un-verifiable by the negative-case
runner, permanently, with no signal.

### The sibling divergence, same root

`tests/lint-vacuous-fixtures.py:44` matches `^\s*#\s*fails-against:\s*\S` -- the BARE spelling
-- so it cannot see the ratified `fails-against-mutation:` / `fails-against-rev:` forms and
flags every file using them as undeclared. Measured 2026-09-03: 11 flagged, of which 2 are
false positives, one being `tests/test_ledger_shrink_cut_after_anchor.sh`, already committed
at `f646f072`.

So the repo has TWO tools disagreeing about the same declaration syntax: the lint rejects the
ratified spelling, and the runner accepts it but cancels it on a roadmap file. **That
divergence is the real bug** -- neither tool is individually wrong about its own rule.

### What is owed

- The carve-out should consult the item's CHECKBOX, not merely the token's presence, so it
  expires when the item closes -- matching `run-tests.sh`'s existing EXPECTED-RED semantics
  rather than inventing a second meaning for the same marker.
- `lint-vacuous-fixtures.py`'s matcher should accept the ratified suffixed spellings.
- Both should derive the spelling from ONE definition rather than each carrying its own
  regex, per `id:4983`.

Until then, a `# roadmap:`-headed test cannot have a machine-verified negative case, and the
honest workaround is what `id:60eb`'s author did: record the mutation and its observed output
as PROSE in the file's comment block, and say why.

- **Acceptance**: a `# roadmap:`-headed test whose item is TICKED has its `fails-against-*`
  declaration executed and verified; one whose item is OPEN is still skipped as roadmap-spec;
  and `lint-vacuous-fixtures.py` stops flagging the ratified spelling.

- **Done-check**: `tests/test_todo_conformance_title_chrome_60eb.sh` (which has a recorded but
  unverifiable mutation today) reports `red-there OK` once `id:60eb` is ticked, and
  `lint-vacuous-fixtures.py`'s count drops by the 2 measured false positives.
