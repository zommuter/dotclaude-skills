# id:1b0d -- the lane-vocab ratchet BLOCKS the pool from ticking any grandfathered old-vocab item

Reported by `code-lawless-c3` 2026-09-10 after it cost a real handback; mechanism verified here
against `hooks/pre-commit-lane-vocab.sh` before accepting. Taken directly rather than routed
through the inbox, because the hook is this repo's.

## The mechanism

`relay/scripts/roadmap-tick.sh` flips `- [ ]` to `- [x]` **on the item's own line**. So a
grandfathered `[HARD - pool]` line arrives in `git diff --cached` as an **ADDED** line carrying old
vocabulary. `hooks/pre-commit-lane-vocab.sh` scans added lines only:

* `:152` reads `git diff --cached -U0 -- . ':(exclude)*.archive.md'`;
* `:155-157` keeps a line only if it starts `+`, then matches a checkbox and extracts its lane tag;
* it **never looks at the corresponding `-` line**, so it cannot tell a re-presented line from a
  genuinely new one;
* the only carve-out is `*.archive.md` (`:139-143`, `id:2065`).

**So the ratchet fires on the one edit that introduces no new old vocabulary at all.** Closing a
grandfathered item through the sanctioned path is impossible by construction, in every
relay-onboarded repo.

## The cost, which is out of proportion to the size

On `code.lawless` the executor's work MERGED (`cd2561a`) and only the TICK failed:

    integrate.sh handback: handback=roadmap-tick handbackCode=31
    handbackReason=roadmap tick commit failed for ids '5ac0' landed=false

That leaves the ledger **staged but uncommitted in the main checkout**, which then refuses the next
writer's `md-merge --commit` on the same file, since a scoped `git add -- TODO.md` sweeps in
whatever else is staged there. One blocked tick therefore blocks the next unrelated ledger write.

## The fix, and why the obvious alternative is wrong

**Exempt a line whose ONLY change is the checkbox state.** Compare the added line against its
removed twin with the checkbox masked; if they are otherwise byte-identical, the edit introduces
nothing and must pass. A genuine re-add has no such twin, so the two cases stay distinguishable.

Rejected alternative: **require convert-then-tick as an ordering discipline.** That is what we have
now by accident, and it puts the burden on whoever happens to trip it -- which today was an
unattended pool, the one actor that cannot exercise judgment or ask. It also means a human must
convert a repo's grandfathered tags BEFORE the pool is ever allowed to close one, an ordering
nobody knows to enforce and nothing checks.

## Two adjacent findings from the same incident, recorded not merged

* **`[HARD - hands]` cannot be auto-cleared ahead of a tick.** `lane-convert.sh` deliberately
  refuses it: it fragments across four capability-keyed candidates and needs per-item human
  judgment (`relay/scripts/lane-convert.sh:16-18`, `id:3ef7`). 2 of the 6 lines are that shape, both
  in `code.lawless`, and the peer has put the choice to the owner rather than guessing. So even with
  the checkbox-masking fix, those two need a human before they can be closed -- the fix removes the
  mechanical block, not the judgment call.
* **`md-merge --commit`'s atomicity does not hold against a concurrent writer staging the same
  file.** Its `git add -- <file>` is path-scoped, not hunk-scoped, so it commits or rolls back
  another writer's staged work along with its own. It rolled back correctly in this incident
  (`id:4b64`), so nothing was lost, but the `id:aa93` dirty-guard story assumes a single stager per
  ledger. Worth its own item if it recurs.

## Acceptance

* A commit whose staged diff changes ONLY `- [ ]` to `- [x]` on a line carrying a grandfathered
  old-vocab lane tag is ALLOWED.
* A commit that ADDS a new old-vocab lane tag is still BLOCKED (the ratchet's whole purpose).
* A commit that changes the checkbox AND the lane tag text is still BLOCKED.
* `roadmap-tick.sh` can close a grandfathered item end-to-end without `--no-verify`.
