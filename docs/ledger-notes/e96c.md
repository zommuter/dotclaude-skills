### The defect

`relay/scripts/discover-sig.sh` promises to hash a SUPERSET of every input the classifier
shard reads. After the `id:0d7c` trim it no longer does.

Measured, not reasoned:

```
1 baseline clean       : 0d9f5f0caba09f7d
2 ROADMAP.md edit #1   : d38bec97466ad6d0
3 ROADMAP.md edit #2   : 01067388d5d68f99   <- content-hashed, moves per edit
4 note 9d06 edit #1    : 16ca905d7c1b126e   <- porcelain gains an M line
5 note 9d06 edit #2    : 16ca905d7c1b126e   <- IDENTICAL
6 note 9d06 edit #3    : 16ca905d7c1b126e   <- IDENTICAL
7 note edit COMMITTED  : d84b4c71ad445648
```

It content-hashes `ROADMAP.md` and `ROADMAP.archive.md`, but **not `TODO.md` and not
`docs/ledger-notes/`**. Notes reach the signature only through `git status --porcelain`, which
records THAT a file changed, never WHAT changed. So three substantively different edits
collapse to one signature.

### Why this is a real contract violation

`discover-chunk.sh` runs `classify-repo.sh`, which stats 53 ROADMAP-pointed and 693
TODO-pointed note files to compute `roadmap_bytes`/`todo_bytes`. **Those note files are shard
inputs that the signature does not hash**, so the superset promise is broken in the one
direction CLAUDE.md names as the only hazard: UNDER-invalidation, where `relay-loop.js` reuses
a stale verdict because the signature did not move.

### Stated precisely rather than overclaimed

The exposed window is an **UNCOMMITTED** note edit to a file that is already dirty. A committed
edit moves HEAD and the signature with it. So this is narrow.

But it is a regression created by the trim: pre-trim, that prose lived in content-hashed
`ROADMAP.md` and any edit moved the signature. Post-trim it does not. And the window widens
with every repo migrated.

**Severity is UNMEASURED.** The reachability of the uncommitted-edit window in a real pool
round was not measured, and this note does not claim it.

### The fix, and the trap in it

Hash the pointed-to note files. Over-hashing is free by the tool's own contract -- it merely
wastes a re-classify, while under-hashing is the correctness hazard.

**The trap:** it must derive the notes directory from the item's POINTER, not from a hardcoded
`docs/ledger-notes`, or it inherits `id:d4d3`'s blindness on the 45 repos that name it
differently.

- **Acceptance**: editing a pointed-to note file changes the repo's discovery signature, both
  committed and uncommitted; the notes directory is derived from the pointer; and fail-open is
  preserved (an empty or sentinel signature still re-classifies).

- **Done-check**: repeat the seven-step sequence above and confirm steps 4, 5 and 6 produce
  three DIFFERENT signatures where they produce one today.
