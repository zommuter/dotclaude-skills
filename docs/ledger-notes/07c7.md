# id:07c7 -- the dispatch LOCKOUT LOOP, diagnosed as one loop rather than three bugs

Umbrella over `id:7f4c`, `id:40cf`, `id:5f6a`. Filed 2026-09-10 after the 2026-09-09 evening

## The loop

    context death parks an orphan
      -> orphan suppression empties the nameable id set
        -> the unnamed unit loses its ledger slice
          -> the prompt-size gate sizes WHOLE ledgers
            -> every execute dispatch is refused
              -> no work lands, so more units die the same way

`id:7f4c` is that loop stated as a mechanism. `id:40cf` is the step that makes it bite hardest:
the whole-ledger path charges all 714 pointed-to notes, about 89% of a 603k-token estimate --
the exact corpus `id:0d7c`'s trimming exists to keep OUT of any context. `id:5f6a` is why it
can run unseen: `transcript-shape-preflight` case (C) SKIPPED exits 0, so the detector reports
its own diagnostic outcome as green.

## Why ONE diagnosis and not three tickets

Each of the three was found by a different session hitting a different face of the same loop,
which is exactly the shape that produces three partial patches and no fix. The loop has a
cheapest cut and the three items cannot be ranked against each other while they sit in separate
tickets: on present evidence `id:40cf` looks like the highest-yield single cut, because the
whole-ledger charge is what turns a missing slice into a REFUSAL rather than merely a large
prompt -- but that is a hypothesis to test inside the loop, not a conclusion.

**Sequencing judgment, stated so it can be argued with:** fix `id:5f6a` FIRST even though it
is the smallest. While a detector reports SKIPPED as green, any measurement taken of the other
two is taken through an instrument that cannot say "I did not run". That ordering is about
trusting the evidence, not about yield.
