# id:0246 -- `scan-routed.sh` tokenises an inbox line by FIRST marker, `append.sh` by TRAILING marker; they disagree on 2 of 2 live items

**HIGH, live right now, and PRE-EXISTING** (not caused by `id:1d83`; verified both tokens below
are ACCEPT under the old two-file predicate as well). Found by the `id:1d83` adversarial review,
2026-09-10, and independently reproduced.

## The divergence

`relay/scripts/scan-routed.sh:227` picks the token with

    grep -oP '(?<=<!-- routed:)[0-9a-f]{4}(?= -->)' | head -1     # FIRST match on the line

`meeting/append.sh` requires the marker to be TRAILING (`\s*$`) on a `- [` line -- the
`id:411d` anchoring. On any inbox line that PROSE-CITES another token, the two parsers pick
different tokens. Both live inbox lines do exactly that:

| inbox line | scan-routed picks | append.sh owns | all markers on the line |
|---|---|---|---|
| `[cartulary]` | `b71e` (a quoted citation) | `3e13` | b71e 20ce 3e13 |
| `[meeting-rpg]` | `113e` (quoted in backticks) | `cef7` | 113e cef7 |

That is a false read on **2 of 2** live items, i.e. every item currently in the inbox.

## What `--apply` does today

1. scan-routed resolves the WRONG token, finds its quoted twin, and reports
   `RESOLVABLE routed:b71e -> [cartulary] (already landed ...)`.
2. `--apply` then calls `append.sh inbox-done b71e`. No inbox line OWNS `b71e`, so inbox-done
   takes its "nothing to delete" branch and exits 0.
3. scan-routed swallows that (`2>/dev/null || true`) and prints `RESOLVED ... removed from
   inbox` -- **while the line survives**. A silent no-op reported as success, which is the
   `id:4347` ban and the `id:d35a` failure class in one.
4. The GENUINE tokens `3e13` / `cef7` are never evaluated, so the real dead-letter question is
   never asked for either item.

## AMENDED 2026-09-10: it is a THREE-way disagreement, not two (an edit, declared per the
## notes-are-editable rule)

`code-lawless-c3` read the installed files rather than this note and found a third spelling. There
are three live rules for "which token owns this line", and all three differ:

| site | rule | on a line whose marker is followed by prose |
|---|---|---|
| `scan-routed.sh:226` | FIRST marker (`head -1`) | `bbbb` |
| `append.sh:707` (the `add` path) | LAST marker (`tail -1`) | `bbbb` |
| `append.sh` `inbox-done` (python) | marker at END OF LINE (`\s*$`) | **NO token at all** |

Measured on `- [ ] [tgt] cites \`routed:aaaa\` in prose <!-- routed:bbbb --> trailing note`.

**The third row is a worse defect than the one this item was filed for.** Trailing prose after an
id marker is EXPLICITLY legal (`id:798d`, e.g. `<!-- id:XXXX --> -- GATED (auto, id:3801)`), and
such a line is owned by NO token under `inbox-done` -- so it silently takes the "nothing to delete"
branch, exits 0, and can never be resolved, while `scan-routed` happily reports it RESOLVED. A
legal line shape is unresolvable by construction.

So the acceptance below is widened: the shared extractor must agree with `id:798d` (a marker
followed by trailing prose still OWNS its token), and all three call sites must adopt it. Fixing
only the `head -1`/`tail -1` pair would leave the legal-line-shape hole open.

## Why this is the same bug twice, which is the argument for where to fix it

While measuring `id:1d83`'s open question, this session wrote a throwaway probe that extracted
inbox tokens with a bare `grep -oE 'routed:[0-9a-f]{4}'` and broke on both live lines for
precisely this reason -- three tokens came back per line. It was fixed by copying `append.sh`'s
trailing-marker anchoring. So the anchoring has now been re-derived from scratch, wrongly, twice:
once by `scan-routed.sh` in production and once by an ad-hoc probe an hour before this was filed.

**Therefore: do not fix this by patching `scan-routed.sh`'s regex in place.** The token-extraction
rule belongs in `relay/scripts/lib-anchored-id.sh` beside `token_marker_in_files`, as a named
`inbox_line_own_token` helper that both callers use. `lib-anchored-id.sh` already owns the
OWN-MARKER predicate; it does not yet own OWN-TOKEN EXTRACTION, and that gap is what both
re-derivations fell into.

## Acceptance

* A new shared extractor returns the TRAILING `routed:` marker of an inbox line and nothing else.
* `scan-routed.sh` uses it; a line citing foreign tokens resolves to its own token.
* A fixture inbox line carrying a prose citation plus its own trailing marker yields only the
  trailing token, asserted for BOTH callers so they cannot drift apart again.
* The silent-no-op path is made loud: if `inbox-done` reports nothing to delete, scan-routed must
  NOT print `RESOLVED`.
