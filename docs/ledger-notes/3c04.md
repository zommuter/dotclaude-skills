### Why it cannot work as designed

The gate is a decision about a **unit**. `git push` is an operation on a **ref**. A push
cannot carry commit N+1 while leaving commit N behind on the same branch, so once a
substantive unit is merged to `main`, the next push of `main` publishes it no matter what
the queue says.

`integrate.sh` step 8 states the mechanism plainly: *"A NON-SUBSTANTIVE unit is UNCHANGED:
every remote is pushed, as before."* So four substantive units deferred their public push
this run, and the fifth unit -- a non-substantive review at 18:07 -- pushed every declared
remote and carried all four with it.

The `id:99b7` allowlist does **not** cover this. It made UNDECLARED remotes unconditional,
explicitly so the non-substantive path "can no longer push everything". But GitHub here is
*declared and public*, which is the `push GATED by ratification` branch, and that branch is
still defeated by any later non-substantive unit in the same repo.

This is a granularity bug, not a bad goal. That distinction is what makes deleting the
mechanism the wrong default.

### The options

**A. Change the gate's granularity from the unit to the REMOTE.** Never push a
declared-public remote while any unresolved queue entry for the repo is an ancestor of
`HEAD`. Small: roughly a dozen lines in `integrate.sh`, reusing the existing queue and
`git ls-remote`. Cost: the public repo stalls until the owner ratifies, so staleness equals
owner latency -- and the owner is already the bottleneck across ~40 repos.

**B. Keep unratified work off `main`.** Land substantive units on a staging branch and
fast-forward `main` only after ratification. This is the only option that preserves both
"the pool keeps working" and "nothing publishes unreviewed". It also restructures the
integration model the whole relay rests on (one writer to main, integrator merges to main),
so it is disproportionate to the problem unless A proves intolerable.

**C. Drop the gate; move the control to merge time.** If it must not be public, it must not
be on `main`. Replace the queue with a pre-merge check and delete the queue. Honest, but
gives up any post-hoc hold.

**D. Make the queue self-verifying** (orthogonal, and required under A and C alike). Resolve
or retire entries whose commit `git ls-remote` shows is already public, so the queue stops
reporting a false state.

### DECIDED 2026-09-02 (owner): A plus D

Owner ratified **A + D**. B and C were not taken. Implementation is `id:7408`
(`children-of:3c04`). The 17 existing entries were closed the same day.

**One correction to the recommendation as originally put, made before acting on it.** It
said "retire, do not resolve" the 17, reasoning that `resolve` would falsely assert the
owner had ratified them. That is wrong about what the verbs store. `ratify-queue.sh`'s own
docstring defines them as `resolve` = *"the remote demonstrably carries this"* (evidence:
`verified_sha`/`resolved_ref`) and `retire` = *"this can never land, and here is why"*
(never runs a remote check, writes no landing evidence). All 17 **had** landed, so `retire`
would have recorded a false "can never land" and destroyed the landing evidence. `resolve`
is the factually correct verb, and `verify` confirms LANDED for them.

They were therefore resolved, each carrying a `--note` recording that publication was
INVOLUNTARY -- via the non-substantive push path, not by owner review -- so a later reader
cannot mistake the entry for a reviewed publication. That preserves the one fact that
mattered in the original "retire" instinct, without the false claim.

- **D is mandatory whichever way A/B/C goes.** A mechanism with 0/17 efficacy *and* a
  misleading readout is worse than no mechanism, because "pending" reads as "not yet public"
  and someone will eventually act on that belief.
- **A over C**, because the goal is legitimate and the failure was mechanical. Deleting a
  safety mechanism that failed for a fixable reason discards the intent along with the bug.
- **A over B for now**, on proportionality. Revisit B only if A's staleness proves
  intolerable in practice; that is a cheap experiment to run and an expensive one to
  pre-empt.
- **Retire, do not resolve, the 17.** They cannot be un-published, so holding them pending
  is meaningless. Use `ratify-queue.sh retire <ckpt> --reason ...`, which exists precisely
  for entries that can never resolve. `resolve` would falsely assert the owner ratified
  them, and there is deliberately no `resolve --force`.

### The risk in A worth stating

A makes the owner a hard blocker on public publication. If ratification latency is measured
in weeks, the public mirror silently goes stale, and a stale public repo is its own failure
mode. A should therefore ship with the stall being LOUD -- surfaced per run, not only
visible to someone who runs `ratify-queue.sh list`.
