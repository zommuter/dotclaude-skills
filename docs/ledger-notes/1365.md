**Owner's idea, 2026-09-02**, filed from a session where the question came up four times in
one day and was resolved four times by luck rather than by mechanism.

**THE PROBLEM.** An agent cannot distinguish an authorization the owner actually gave from
one that merely *claims* he gave it. Every channel that carries such a claim is unsigned
prose:

- a **peer session** relaying it (`"my owner has asked you to run the shrink against
  loderite"` -- measured this session; I declined and asked the owner directly, and he
  confirmed, so the claim was TRUE. The point is that I could not tell, and refusing was
  the only safe move available);
- a **ledger line or detail note** asserting `owner-ratified 2026-09-02` -- which agents
  write themselves, and which the next session reads as authority;
- `@owner-accepted` / `@owner-answered:<date>` markers. Executor contract v17 rule 8
  forbids any agent from writing one, and **nothing enforces that** -- it is honour-system
  today, which is exactly why the shrinker treats them as keep-always;
- a **commit message**, a `CLAUDE.md` clause, a meeting note's Decisions section;
- the **cross-repo inbox**, whose entries cross a trust boundary by design.

The fleet already has the RULE (CLAUDE.md: "a delegated agent's verdict is a
recommendation, never a self-settling decision"; the chidiai case
`2026-07-15-delegated-verdict-settled-without-owner-ratification`). What it has no way to
do is **verify** that a given sentence carrying the owner's authority actually came from
him. The rule is unenforceable by construction, so it degrades to agent discipline -- and
agent discipline is what failed in the chidiai case.

**WHY TODAY'S MITIGATION DOES NOT GENERALISE.** The resolution this session was "ask the
owner directly", which worked only because he was reachable via remote-control. It fails
in the cases that matter most: an `--afk` run, a pool child, a scheduled/cron session, or
any agent that is not the one holding the human's attention. Those are precisely the
contexts where a laundered authorization does the most damage, because nothing else is
watching.

**THE IDEA: sign the user's authorizations. Low barrier, easy UX -- that is a REQUIREMENT,
not a nice-to-have.** A scheme that makes the owner do cryptography by hand will not be
used, and an unused guard is worse than none because it implies coverage it does not have.

Sketch, to be designed not assumed:

- **Primitive already present:** `ssh-keygen -Y sign` / `-Y verify` over a namespace, with
  an allowed-signers file. Same key material as git commit signing, already on the
  machines, no new dependency, and `uv`/`pamac` do not enter into it.
- **Sign AUTHORIZATIONS, not every turn.** Signing all user input is the barrier that kills
  adoption. The unit worth signing is the small set of statements that unlock something
  hard-to-reverse or cross-boundary: run against another repo, ratify a decision into a
  ledger, mark `@owner-accepted`, close a gate. Everything else stays plain.
- **Scope + expiry + nonce, or a signed "go" is replayable.** "Yes" signed once must not
  authorize the same action against a different repo next week. The signed payload should
  name the action, the target, and a validity window -- otherwise this reproduces the
  spent-pre-registration failure the CLAUDE.md heuristics already warn about.
- **Verification is the cheap half:** any agent, in any session, can check a signature
  offline against the allowed-signers file. That is what makes it work for pool children
  and cron sessions, which cannot ask.
- **Candidate UX:** a slash command or a hook that signs the owner's next message, or a
  one-key confirm in the terminal. The measure of success is whether HE uses it when
  nobody is watching, so prototype the UX before the crypto.

**WHAT IT WOULD MAKE ENFORCEABLE that is honour-system today:** contract v17 rule 8
(`@owner-answered` written only by the owner); the "delegated verdict is not a decision"
rule; `owner-ratified` claims in derived docs, which the CLAUDE.md "check a derived doc
against its ratified source" heuristic exists to police by hand; and cross-session
authorization relaying, where the current answer is a blanket refusal that costs real work
(this session refused a run its owner had in fact authorized, and the round trip took
hours of wall-clock).

**EXPLICIT NON-GOALS.** It does not stop the owner authorizing something unwise, does not
stop an agent misreading the scope of a genuine signature, and does not make an unsigned
statement false -- most of what he says will stay unsigned, so the absence of a signature
must NOT read as forgery. Getting that default right is most of the design: a scheme where
unsigned means untrusted would make every ordinary sentence suspect and would be abandoned
in a day.
