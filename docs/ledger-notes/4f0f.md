## From TODO

`md-merge.py update-ids` **cannot rewrite a WRAPPED multi-line ledger item at all**. `line`,
`append` and `regex_sub` are each scoped to the single physical line carrying the id-marker
comment, but most real TODO/ROADMAP items wrap over 5-15 continuation lines, and the stale
prose is usually in the continuation. Found 2026-09-04 (kienzler-solutions `id:9f11`: every
wrong phrase sat on a continuation line, so the helper could reach none of them).

Consequence: the CLAUDE.md rule "shared non-union ledgers go through the flock'd helper, never
Edit" has no compliant path for the commonest edit there is, which pushes callers to either
leave the ledger stale or ask the owner to authorise an Edit. Both were observed in that
session.

Related: `id:5817` (boxes with no marker at all are likewise unaddressable) and `id:e166`
(multi-line payloads corrupt the marker), so the block-aware rewrite must keep the marker
terminal on the checkbox line.

### The block definition is NOT a new invention -- reuse the one in the repo

`tools/ledger-continuations.py:1334-1338` already defines an item's continuation block, and
that definition is the one to implement against rather than a fresh guess:

```python
j = i + 1
cont = []
while j < n and lines[j].strip() and re.match(r"^[ \t]", lines[j]):
    cont.append(lines[j])
    j += 1
```

So: the block is the `TOP_ITEM_RE` head line plus the consecutive following lines that are
non-blank and begin with whitespace. A BLANK line ends the block; so does the next line at
column 0. Two tools disagreeing about where an item ends would be the `id:4983` defect class,
and this repo has paid for that already (`id:7c82`).

### What to build

An ITEM-scoped mode for `update-ids`, spelled `{"id":"XXXX","scope":"item","regex_sub":{…}}`,
whose `regex_sub` is applied to the block text rather than to the head line alone, under the
same flock. `scope` defaults to `"line"`, so every existing delta keeps its present meaning.

Two refusals are load-bearing, because the failure this repo keeps paying for is a helper that
degrades quietly rather than loudly (`id:4347`, and `id:3bd4` on this very function):

- `scope: "item"` combined with an op this mode does not support (`append`, `line`,
  `insert_before`/`insert_after`) is a LOUD refusal naming the op, never a silent fall-back to
  line scope.
- An unrecognised `scope` value is a LOUD refusal naming the value, never a silent default to
  line scope.

And the `id:e166` constraint survives: after an item-scoped rewrite the head line must still
carry its anchored `<!-- id:XXXX -->` marker terminally, or the item stops being addressable
by the very helper that just edited it.

- **Acceptance**: an item-scoped `regex_sub` rewrites matching text on the item's CONTINUATION
  lines; a delta with no `scope` stays line-scoped; the block stops at a blank line and at the
  next column-0 line, so a neighbouring item and any post-blank prose are byte-identical; the
  head line keeps its terminal id marker; and both refusals above exit non-zero naming what
  was wrong.

- **Done-check**: `tests/run-tests.sh tests/test_md_merge_item_scope_4f0f.sh` is green, then
  `make test` is fully green.

**The `scope` spelling is a JUDGMENT CALL made by the spec, not by the owner** -- filed in
`REVIEW_ME.md`. The behaviour is what the TODO item ratified; the JSON key name is the spec's
choice, taken because it composes with the existing per-op shape instead of adding a parallel
op family, and because `id:5d7e` already folds several ops per id.

Deliberately NOT specced here: item-scoped `append` and item-scoped whole-block replacement.
Both are defensible extensions, but each needs its own answer to "where in the block does the
text land, and what happens to the marker", and neither is required by the incident this item
came from. The refusal above keeps that door open loudly rather than half-open silently.

Cross-reference: `id:3bd4` (a `regex_sub` that matches its id but changes nothing must fail
loud) applies to item-scoped ops too once both land. This spec deliberately avoids asserting
anything about a MISSING pattern so the two specs stay independently red or green.
