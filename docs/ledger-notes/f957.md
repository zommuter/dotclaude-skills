## From TODO

**The `hard` lane can never be sliced, so a big-ledger repo can never be dispatched on it.
`ledger-slice.sh` is not broken; the plumbing simply never hands it the ids it already has.**

**Diagnosed 2026-09-09** after `loderite` handed back for the third time in one run on the
`id:4f9b`/`id:b018` prompt-size gate (~481,978 tok against a 300,000 budget). The handback text
tells the operator to "find why `ledger-slice.sh` produced no `slice_path`". Here is why.

**The mechanism, read from the source rather than inferred.**

```js
const dispatchItemFor = (unit) => unit.inject_item || namedItemsFor(unit)[0] || ''
// and namedItemsFor reads, exclusively:
return (Array.isArray(unit.actionable_routine_ids) ? unit.actionable_routine_ids : [])
```

`namedItemsFor` derives its id from **`actionable_routine_ids`** -- ROUTINE ids only. A `hard`
unit fires precisely when a repo has NO actionable `[ROUTINE]` work, so that array is empty by
construction, `dispatchItemFor` returns `''`, and the slice call takes its no-item branch:

```js
const useReviewSet = !item && unit.verdict === 'review'
if (!item && !useReviewSet) { log('… nothing to slice, fail-open, dispatching with the unsliced brief'); return null }
```

`review` has its own `--since-last-review` derivation and `execute` names a routine id, so
**`hard` is the one verdict that structurally cannot produce a slice.** It is then sized on the
WHOLE ledgers, which for `loderite` (`ROADMAP.md` 834,162 B + `TODO.md` 825,755 B) is an
automatic refusal. The repo is not merely unlucky: it can never be dispatched on this lane
while its ledgers are that size, and it will re-handback on every run forever.

**The ids are ALREADY THERE.** The classifier emits `open_hard_pool_ids`, and `relay-loop.js`
already parses it -- `hardPoolIdsFor(unit)` exists a dozen lines above `dispatchItemFor` and is
used to build the prompt's item survey. Nothing needs to be collected, plumbed from the
classifier, or added to `discover-repo.sh`. The two halves are in the same file and do not talk.

**Measured fix, run before proposing it.** `ledger-slice.sh` already accepts a CSV
(`--ids a,b,c`, the id:dd59 multi-item case). Slicing loderite's 24 open `[HARD]` ids:

| | bytes |
|---|---|
| whole ledgers (what it is sized on today) | 1,659,917 |
| `--ids` slice of all 24 hard ids | **21,496** |

**~77x smaller**, roughly 5.4k tokens against a 300k budget. A single-id slice
(`--id a728`) came to 1,102 B, confirming the slicer itself works fine on this repo.

**Why `--ids` and not `--id <first>`.** The `hard` lane's contract is that the CHILD surveys
the open `[HARD]` items and picks one it can finish (the handoff-C5 sizing rule). Slicing on a
single id would silently convert that into named-item dispatch and remove the choice the lane
is designed around. The CSV slice preserves the survey -- the child still sees all 24 items,
their typed edges and TODO twins -- at 1/77th the size. That is why this is a plumbing fix and
not a lane redesign.

**Shape of the change:** in `dispatchItemFor`, or at the slice call site, fall back to
`hardPoolIdsFor(unit)` when the verdict is `hard` and no routine id is named, and pass the CSV
to `--ids`. Keep every existing fail-open branch: an empty list, a thrown call, a garbled
stdout must all still dispatch unsliced exactly as now. **Do not** let this become a path that
can SUPPRESS a dispatch -- the header's own promise is that slicing "can only ever ADD a slice".

**Acceptance:** a `hard` unit on a repo with open `[HARD]` items carries a `slice_path`, and
`loderite`'s hard verdict dispatches instead of refusing at the prompt-size gate.
**Done-check:** a fixture asserting a `hard` unit with `open_hard_pool_ids` produces a slice
call, and one asserting an empty list still dispatches unsliced; `make test` green.

**Caution, from this repo's own history.** `relay-loop.js` prompt-template edits have a runtime
crash class that `node --check` and grep both miss (`id:5bac`/`id:aec5`) -- exercise the
dispatch path, do not merely lint it. And confirm no pool is live before editing (the
in-flight-automation rule).
