# id:ed35 -- `id:1048` GATE 1 binds an orphan to the FIRST `id:` token in its HEAD commit message, which for a commit-and-park residue commit is the MECHANISM's id, not the work item's

Found 2026-09-10 while checking whether `AUTO_INTEGRATE_ORPHANS` was safe to switch on for a trial.
**This must be resolved before that flag is enabled**, because it is the gate that decides whether
unreviewed work can reach `main` without a human.

## The mechanism

`relay/scripts/auto-integrate-orphan.sh` GATE 1 binds the orphan to an item like this:

    item="$(git -C "$REPO" log -1 --format='%B' "$ORPHAN" | grep -oiE 'id:[0-9a-fA-F]{4,}' | head -n1 | cut -d: -f2)"

and then refuses only if THAT item has an OPEN `- [ ]` box on the orphan's own ledgers. An
unbindable orphan (no id token at all) is allowed through on the suite-green gate alone, which is
the ratified A3 position and is fine.

The problem is the middle case: a binding that SUCCEEDS against the wrong item.

## Observed on the live orphan, not constructed

`relay/orphan/relay-20260909-143257-21736-execute-b437-0` has this HEAD commit subject, written by
the `id:f272` commit-and-park path itself:

    chore(relay): WIP UNVERIFIED residue auto-commit for worktree
    relay-20260909-143257-21736-execute-b437-0 (id:f272 commit-and-park; do not treat as reviewed)

`grep -oiE 'id:...' | head -n1` therefore binds it to **`id:f272`** -- the id of the
commit-and-park FEATURE -- and not to `id:b437`, the item the work belongs to. Measured on that
orphan's own ledgers: `f272` has **0** open checkboxes (it is `[x]` in `TODO.archive.md`), so
**GATE 1 PASSES** and the orphan advances to gates 2 through 4.

The commit message it binds from says, in those words, *"WIP UNVERIFIED ... do not treat as
reviewed"*.

## Why this matters more than it looks

GATE 1 exists to catch PARTIAL work ("never auto-close mid-flight work"). Against a residue commit
it cannot do that job at all: it asks about an unrelated, long-closed item and gets a clean answer.
What remains is gates 3 and 4 -- clean 3-way merge and full suite green -- which the ratifying
meeting called "the real safety". That is true as far as it goes, with one caveat established the
same morning this was found: the suite's greenness is not an incorruptible signal. A non-hermetic
test (`id:1975`) had been silently consuming live production state for at least a fortnight while
the suite reported green throughout. A gate whose last line of defence is "the suite was green"
inherits every blind spot the suite has.

Note also that the WORK item's own state is not consulted at all once the misbinding happens, so
"is `b437` finished?" -- the actual question -- is never asked.

## Candidate fixes

1. **Bind by the worktree/branch name, not the commit message.** The orphan branch name already
   encodes the unit (`...-execute-b437-0`), and it is written by the dispatcher rather than by
   prose. Strongest option; the branch name is structured data, a commit message is not.
2. **Refuse to bind from a commit the mechanism itself authored.** A residue commit is identifiable
   (`WIP UNVERIFIED residue auto-commit`, `id:f272`), and the honest disposition for it is
   UNBINDABLE, which routes to the suite-only path rather than a false clean bill.
3. **Exclude known MECHANISM ids from binding.** Weakest: a hand-maintained deny-list of ids that
   are features rather than work items, which rots and is the grandfathering-by-identifier shape
   this repo already has a rule against.

**Recommendation: (1) with (2) as the fallback when the branch name yields nothing.** A residue
commit should never produce a bound-and-cleared verdict; it should produce either the right item or
an honest "cannot tell".

## Acceptance

* An orphan whose HEAD commit is an `id:f272` residue auto-commit does NOT bind to `f272`.
* It binds to the work item named by the branch, or is treated as UNBINDABLE -- never cleared.
* An orphan whose bound work item still has an open box is still refused (the existing behaviour
  must not regress).
* A genuinely complete, correctly-bound orphan still passes, so the `ce50` interrupted-integration
  case the feature exists for keeps working.
