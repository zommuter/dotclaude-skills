# id:b87b -- the id:b54b hermeticity backstop fires on the runner's OWN branch advancing

Found 2026-09-05 by the chain-end review of run `relay-20260905-113859-5807`, by tripping it.

## What happened

`tests/run-tests.sh` reported:

```
HERMETICITY BREACH (id:b54b): the test run left new relay/* refs and/or worktrees in
<worktree> -- a fixture reached the real repo instead of its own mktemp sandbox.
Diff (before -> after):
       | < refs/heads/relay/relay-20260905-113859-5807-review-repo-0 acba57d9...
       | > refs/heads/relay/relay-20260905-113859-5807-review-repo-0 5d388655...
```

No ref was added. No worktree was created. The single differing line is the runner's OWN
current branch, moving because the review child committed its work while the suite ran --
which is what the executor contract tells it to do (`commit in the worktree as you go`).

## Why it is structural rather than bad luck

`snapshot_repo_state()` (`tests/run-tests.sh:113`) emits
`git for-each-ref --format='%(refname) %(objectname)' refs/heads/relay/`, and the guard
fails on ANY difference between the before and after snapshots. Two facts make the false
positive guaranteed rather than incidental in relay work:

1. every relay worktree branch is named `relay/<runId>-<verdict>-repo-N`, so it is always
   INSIDE the watched `refs/heads/relay/` namespace; and
2. the snapshot records `%(objectname)`, so a commit on that branch is a diff even though
   the set of ref NAMES is unchanged.

The guard already carries one carve-out for a known spurious class (harness-created
`.claude/worktrees/` entries, added because concurrent agents tripped it). This is a second
one, and it is the class the guard's own consumers hit most often.

## Cost, and why the message makes it worse

The suite is the definition-of-done check, and this failure is terminal (`exit 1`)
independent of every individual test result -- so a review turn that has committed cannot
get a green suite at all without a second full run. Measured here: one extra full run, at
`load average: 20.52`.

The message compounds it by asserting the wrong finding. It says the run left NEW refs
and/or worktrees and that a fixture reached the real repo; neither is true here, and a
reader following its advice re-runs suspect files one at a time hunting a leak that does
not exist.

## Acceptance

A commit made on the runner's OWN current branch during a run does NOT raise a hermeticity
breach, while a fixture creating or deleting any other `refs/heads/relay/*` ref, or moving
one it does not own, still does. The narrow fix is to exclude the ref that `HEAD` points at
from the object-name comparison -- NOT to drop object names entirely, which would stop the
guard noticing a fixture force-moving some other relay ref.

The message must also match what was actually observed: an added ref, a removed ref and a
moved ref are three different findings and only the first is "left new relay/* refs".
