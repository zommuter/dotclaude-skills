— when the serialized integrator has ≥2 verified worktree branches that are mutually NON-CONFLICTING and completed within a short window, consider a single `git merge --no-ff branchA branchB branchC` (octopus) → ONE integration commit + ONE checkpoint + ONE push, instead of N sequential `--no-ff` merges + N tags + N pushes. Benefits: less RELAY_LOG/tag noise, fewer pushes, faster drain. Decision-call / constraints: (a) the octopus strategy REFUSES on any conflict, so it's only valid for provably-disjoint file sets — the SAME independence test that licensed running them in parallel; (b) loses per-track checkpoint granularity (relay tags per-track today) — a single bad track can't be cherry-excluded post-merge as cleanly, so prefer sequential when any track is unverified/risky; (c) attribution: the combined ckpt message MUST enumerate each track's id + summary. Heuristic: octopus when N≥2 disjoint + each individually gate-verified + close-in-time; fall back to sequential when tracks share files or need independent checkpoints/bisect points. Observed first-hand 2026-06-17 (zkWhale demo-chain): THEME + emoji-svgs + logo were near-independent and finished within minutes — a 3-way octopus would have collapsed 3 merges/tags/pushes into one.   - **Field report -- zkWhale demo-chain run, 2026-06-17/18 (~20 background agents, directed `/relay --afk`):** Ran ~20 worktree children in waves of 1-3, integrated sequentially (merge → full gate → ckpt-tag → push) ≈20×. Findings: (1) **Conflicts were NOT the bottleneck** -- disjoint file-scoping *in the child prompts* prevented nearly all of them; the real tax was the repeated **per-merge integration ceremony**, dominated by re-running the full gate each time (`pnpm test` ~8-15 s + typecheck + lint) plus a push apiece. Octopus's win here is halving *gate-runs + pushes* for co-ready disjoint waves, more than the tag/log noise. (2) **Octopus opportunities genuinely arose ~4-5×** (THEME+emoji-svgs; spinrot+logofix; the two logo rounds; proofglyph+badgesvg) -- each ≥2 branches, file-disjoint, individually green, finished within minutes. (3) **The octopus-blockers that actually recurred were a small set of high-churn shared files:** `strings.ts` (almost every UI agent appends copy -- distinct keys so git *auto-merged*, but it's the #1 risk), `package.json`/`pnpm-lock.yaml` (new devDeps: vite-plugin-singlefile, jimp, potrace), hot UI files like `ArtifactScreen.tsx` (touched by demo-mount/spinner/emphasis across waves), and the ledgers (`TODO.md`). Plus genuine **dependency chains** forced sequencing regardless of merge strategy (a8c2-wiring after the spinner work; demo-transparent-drop after demo-polish). (4) **Deterministic eligibility predictor that would've worked:** pairwise-intersect `git diff --name-only main..<branch>` across the co-ready candidates; empty intersection ⇒ octopus-safe. (5) **Granularity downside barely bit this workload** -- every track was gate-verified *before* merge, so I never needed to bisect/cherry-exclude a track post-integration; a well-formed combined ckpt message preserved the attribution that per-track tags gave. (6) **Recommended impl:** optimistic octopus -- `git merge --no-ff b1 b2 …` (git refuses cleanly on conflict, no half-merge), fall back to sequential for the conflicting subset; gate ONCE after the merged result; run `pnpm install` once if any branch touched the manifest (orthogonal to merge strategy but required before the gate). Net: for this run, a file-intersection-gated optimistic octopus would have cut ~5-7 of the ~20 integration cycles (~30%) with negligible downside. (field report 2026-06-18)
