## From TODO

**The `agent-failures` counter (`id:06a1`) is BLIND to the failure class that actually kills
executors.** Measured in run `relay-20260908-174448-4421` on 2026-09-08.

`RELAY_STATUS.md` reported `agent-failures=2`. The real count of failed children was **7**,
and the two sets are **disjoint**:

| What `agent-failures=2` counted | What it missed |
|---|---|
| `release:zom.fi:claim` -- agent resolved null/empty (the shape a harness-side block leaves, `id:83c2` class) | 5 execute children killed by `Prompt is too long` (dotclaude-skills x3, zom.fi, trustless-ai) |
| `provision:wisenheimer` -- MECH-ERROR exit 255, branch already exists | |

So the counter tracks *mechanical hop* failures and does not see *child deaths* at all. A
prompt-too-long death lands in the HANDBACK stream instead, where it is
indistinguishable-at-a-glance from a legitimate contract handback (an item too big to finish
safely, a `@needs-auth` wall, a size-out refusal).

**Why that is the damaging part.** The counter's name and its `id:06a1` gloss --
"hops/children that failed with no handback" -- promise child coverage. An operator reading
`agent-failures=2` alongside `completed=16` concludes the run was healthy. It was not: a
third of all execute children died. The number was not wrong about what it counted; it was
wrong about what a reader takes it to mean, which is worse, because nothing looks broken.

**Suggested fix.** Either count a child death in `agent-failures`, or -- better, since the
handback stream is where they land -- classify handbacks at emit time into CONTRACT
(size-out, gated, needs-auth, investigated-and-green) versus DEFECT (child died, guard
false-fired, infra failure), and surface the defect count separately. This run's split was
14 handbacks = 5 deaths + 3 gate refusals + 3 legitimate size-outs + 1 legitimate
investigated-green + 1 infra + 1 integrate tick failure, which is a far more useful line
than `agent-failures=2`.

calm while something is wrong".
