## LOCALIZED 2026-09-08 -- the cause is one missing `idx += 1`, and the fix is one line

Edit declared per the README notes-are-editable rule; everything above is retained and this
section is appended. This discharges the "localizes the hang and states the cause" half of the
Acceptance above.

**The cause.** The branch replaces `for lineno, line in enumerate(lines, start=1)` with a
hand-rolled `while idx < n_lines` loop (`meeting/md-merge.py:440`), which makes advancing the
cursor the author's job on EVERY path. Three paths got an explicit `idx += 1` (lines 463, 470)
or an equivalent `idx = j` (line 516). **The loop's fall-through path got none** -- there is no
`idx` assignment anywhere after line 517. Any line reaching the `if item_id in ops_by_id:` fold
appends to `result` and loops back with `idx` unchanged, so the same line is reprocessed
forever and `result` grows without bound. It is a hang and a memory leak, not merely a hang.

**Why `regex_sub` specifically.** The fold path is what a `regex_sub` op takes. A whole-line
`line` op returns earlier, which is why a trivial invocation of the branch's script looks
healthy -- the first probe run here did exactly that and read as fine.

**Measured, both directions, same op and same input:**

| | `update-ids` with one `regex_sub` |
|---|---|
| branch `4f7162df` | `rc=124` (timeout) |
| `main` | `rc=0` |

Diagnostic route, recorded because two earlier attempts misled: piping the test to `tail`
buffered its output and showed nothing, which read as "hangs before the first assertion";
`bash -x` showed the last executed command; `timeout -s INT` produced a Python traceback
inside the loop body. The traceback line is where the spin happened to be interrupted, NOT the
defect -- the defect is the absent increment, found by scanning the loop body for `continue`
paths and their increments.

**The fix, applied and MEASURED in a throwaway worktree (not committed to the parked branch).**
Adding a single `idx += 1` at the end of the fall-through path takes all four named tests from
`rc=124` to **`rc=0`**, at load 4.09:

```
test_md_merge_update_ids_strict  rc=0
test_md_merge_same_id_ops_5d7e   rc=0
test_md_merge_silent_noop_3bd4   rc=0
test_md_merge_item_scope_4f0f    rc=0
```

**`main` is NOT affected.** It still carries `for lineno, line in enumerate(lines` and has no
`while idx < n_lines`. The defect exists only on the parked branch; nothing is at risk today.

**What remains before `id:3bd4`/`id:4f0f` can land, and why it is not free.** The branch is 171
commits behind, and `meeting/md-merge.py` HAS diverged on `main` since (122 insertions / 82
deletions between the two versions) -- unlike the `id:4d65` salvage, where `ratify-queue.sh`
was untouched on `main` and the branch's files applied cleanly. So this is a port, not a
cherry-pick, and the one-line fix above is necessary but not sufficient. The honest estimate
is a small porting job plus a re-run, not a one-line commit. **Owner's call whether to spend
it**; the branch stays parked as the evidence until then.
