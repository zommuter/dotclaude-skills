## From TODO

(found 2026-08-01, `/meeting` ledger-hygiene sweep) — when `/relay human` captures an owner decision and promotes the item, it appends the decision prose and writes the ROADMAP twin, but never touches the TODO line's HEAD TAG. **Observed the same day, 15 minutes apart:** `id:8df5` was decided (build (B)) and promoted to `ROADMAP.md` as `[HARD]`, yet its TODO line still read `[INPUT — decision]`, so the very next `classify.sh` run reported it as pending human input — a decision that had already been made. The stale tag is not cosmetic: `[INPUT — decision]` is what keeps an item OUT of the pool's dispatchable set, so a resolved item stays invisible to the pool for as long as the tag survives. Fix in `relay/references/human.md`'s write-back step (§5): when a decision RESOLVES an `[INPUT — *]` item, the same `md-merge.py` call that appends the decision must also rewrite the head tag to the lane the resolution implies (`[HARD]`/`[ROUTINE]` if it became buildable, `[x]` if it closed) — and when the implied lane is not unambiguous, SURFACE it rather than guess (the never-silently-default-a-disposition rule). Acceptance: a fixture item tagged `[INPUT — decision]` that is resolved-and-promoted comes back from `classify.sh` in a dispatchable class, not `HUMAN`.
