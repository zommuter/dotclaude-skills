## From TODO

`git -C . -c core.pager=true status --short` executed with NO prompt — the injected `-c` sits inside the wildcard and is auto-approved. `-c core.pager=<cmd>`, `-c core.sshCommand=`, `-c alias.x=!sh -c …` and `--exec-path=<dir>` are all arbitrary-execution primitives, so this was an explicit blessing of a sandbox escape. **There is NO safe way to express it with this matcher** — I checked the obvious mitigation and it FAILS: narrowing the prefix to `git -C /home/tobias/src/* status` does not help, because the wildcard still spans forward to the subcommand and can absorb `x -c core.pager=evil`. Enumerating exact repo paths would take ~660 literal entries (allowlist matching is literal, and both `~` and absolute forms are needed) and still would not close it. **DONE ALREADY: all 11 entries deleted from `~/.claude/settings.json` (allow 795 → 784), owner-authorized.** They were HAND-ADDED and unmanaged — `make print-allowlist` emits zero of them — so `tools/allowlist.py` will not reintroduce them; that unmanaged-entry problem is `id:9320`'s complaint with a live consequence. Practical cost of the deletion is likely near-zero today because `defaultMode` is `auto` (an absent command is auto-approved anyway); it withdrew an explicit blessing rather than adding friction, and stricter modes will now prompt. **THIS ITEM = the structural fix:** a read-only `git-read.sh <dir> <subcommand> [args…]` that REFUSES any `<dir>` beginning with `-`, refuses `-c`/`-C`/`--exec-path`/`--git-dir`/`--work-tree` anywhere in its own argv, and shells out to git only for a fixed whitelist of read subcommands (status/log/diff/show/rev-parse/branch/remote/stash list/config --get). Allowlisted as a FIXED SCRIPT PATH (`Bash(~/.claude/skills/…/git-read.sh *)`) — the trailing-wildcard-after-full-command shape, which is the safe one and which 348 existing entries already use. This is the same "deny the raw form, route through the gated script" pattern as `relay/scripts/force-push.sh` and `worktree-retire.sh`. **Gate on evidence, per observe-before-preventing:** only build it if the deletion actually costs prompts in practice — under `defaultMode: auto` it may cost nothing at all, in which case this item closes as won't-need.
