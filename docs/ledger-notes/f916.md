## From TODO

The rule already says to check whether a project has an existing tool before building one, but it fired zero times on a real 2026-08-12 loderite lapse: a new tool wrote into docs/roadmap-notes/, which ALREADY existed with 10 git-tracked files from a prior pass, and its unconditional writeFileSync OVERWROTE 5 of them (3d11 4277->1850 bytes, bc0e 4420->2112, d215 3783->2917, ca44 5029->4378). Nothing caught it — no test, no typecheck, no tool output. It surfaced ONLY because the operator reconciled the tool's printed 'items to extract : 30' against 'ls | wc -l' = 35. Two concrete additions worth making, both cheap: (1) extend the rule from 'check for an existing TOOL' to 'check for an existing OUTPUT DIRECTORY' — git ls-files <dir> before writing a tool that creates files there; a tracked file means a convention exists, read one and match it. (2) State the invariant that a file-writing tool must never writeFileSync over a path it did not create — append under a distinct heading, or refuse loudly and list collisions. Context that makes this worth generalising: the same session had a SECOND instance (shipping check-ledger-duplicates.mjs without reading tests/roadmap-archive.test.ts case 19, which already asserted half its rule), caught by a review agent — so it is a recurring shape, not a one-off. The count-reconciliation habit is the cheapest known detector and is currently nowhere written down. <!-- id:f916 -->
