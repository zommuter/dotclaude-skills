## From ROADMAP

### What this is

The `id:0d7c` head-line LENGTH RATCHET reads a COMMITTED SNAPSHOT
(`relay/head-length-baseline.txt`, whose own header calls itself exactly that). Only a
deliberate `--regen-length-baseline` moves the floor, which is the `cb3e` discipline the
meeting ratified on purpose.

The gap: nothing detects that the snapshot has gone LOOSER than reality. After a shrink
pass every shrunk item keeps its old, larger floor until someone remembers to regenerate,
and until then a regrowth back up to the old value is `length-grandfathered` WARN rather
than `length-regrowth` ERROR. That is silent, and it is the whole hole.

### The founding arithmetic

`id:718c` went **4,367 -> 222 -> 1,316** chars in one afternoon.

```
snapshot floor 4367 : 1316 > 500 and 1316 <= 4367  ->  length-grandfathered  WARN  (silent)
regenerated to  222 : 1316 > 222                   ->  length-regrowth       ERROR (fires)
```

The ratchet cannot catch its own motivating incident until the floor is re-cut. So the
regen is not hygiene, it is load-bearing, and forgetting it is indistinguishable from
compliance.

### The check

Pure READ, no writes, no flock, no dirty tree: for every baseline entry, report when the
item's CURRENT head length is BELOW its baselined value. That single comparison is the
whole predicate.

```
current < baselined   ->  BASELINE-STALE: the floor forgives more than reality requires;
                          regenerate with --regen-length-baseline and commit.
```

Report the per-entry slack and the total, so the size of the hole is visible rather than
just its existence.

### Why a detector and not self-tightening (owner-ratified 2026-09-02)

Self-tightening was the alternative and was rejected. It would give a READER a write side
effect: `todo-conformance.sh` is a reporter, and writing the committed baseline on every
run dirties the tree, which the `id:aa93` guard turns into a DEFERRED relay dispatch. It
would additionally need a flock for concurrent sessions, and a concept that does not exist
today -- which invocation is AUTHORITATIVE -- because the checker also runs against
fixtures, worktrees and hermetic tests, and a fixture run that tightened the real baseline
would poison it.

The shape adopted here already has precedent in this repo: `mech-currency.sh` (`id:0384`)
detects that a live proxy's in-memory allowlist is stale versus the source on disk, fails
closed, names the remedy, and deliberately does NOT auto-restart the proxy.

### Measured state, 2026-09-02

```
baseline entries                                     61
  exactly AT baseline (frozen, grandfathered WARN)   60
  ABOVE baseline (length-regrowth ERROR)              0
  STALE (current shorter than baselined)              0
over 500 with NO baseline entry (over-budget ERROR)  29
```

Two things follow. First, **the monotonic-shrink half of the ratchet has never fired in
either direction**: 60 of 61 entries sit exactly at their floor. Today the mechanism is a
freeze, and its only active behaviour is rejecting new over-budget lines. Second, the
current `0 stale` is NOT evidence the discipline is safe -- the day's large shrinks
(`id:f193`, `id:40c0`) moved CONTINUATION lines while this ratchet measures HEAD lines, so
they never exercised it at all.

`id:64f9` (the 257 title rewrites) is the first pass that will move head lines in bulk, and
it is exactly where a stale floor would silently forgive every subsequent regrowth. This
detector should exist before that pass runs, not after it.

### Scope

- Report-only, like the rest of the length family's WARN classes. It must not regenerate
  anything, and it must not block.
- Its finding should name the remedy command, not merely the condition.
- `*.archive.md` and the inbox stay out of scope, matching the ratchet itself (`id:2065`).
- `id:2d17`'s own saturation baseline reuses this regen-plus-detect pattern rather than
  inventing a second one.

- **Acceptance**:

A read-only check reports every baseline entry whose item's current head length is BELOW its
baselined value, naming the per-entry and total slack and the remedy command. It writes
nothing, takes no lock, and never regenerates the baseline itself.

- **Tests**:

Hermetic fixtures: an entry whose current length is below baseline is reported; one at
baseline is not; one above baseline is left to the existing `length-regrowth` rule. A negative
case proving the check fires, since a detector that cannot fire is the failure this exists to
prevent.

- **Done-check**:

Shrinking a fixture item below its baselined value makes the check report it, and
regenerating the baseline clears the report.
