# id:1d83 -- the id:5355 archive guard keys on a DATE, so an undated same-session close still carries its `routed:` twin out of TODO.md

Observed LIVE 2026-09-10, twice in one session, the second time consequentially.

## What happened

`archive-done.sh` archived `id:1975` within minutes of it being filed and closed. That line
carries `<!-- routed:1d58 -->` -- the durable twin `code.lawless` needs for
`append.sh inbox-done 1d58`. The twin check (`~/.claude/skills/meeting/append.sh:258`,
`token_marker_in_files "$token" "$tgt_path/TODO.md" "$tgt_path/ROADMAP.md"`) does **not** read
`TODO.archive.md`, so the peer's resolution would have refused with exit 3 and their inbox line
would have been stuck, unresolvable, with the target item already closed.

Caught only because the archive pass was run in the same session that filed the item and its
diff was read. A later session would have seen a refusal with no obvious cause.

## Why the existing guard did not fire

`archive-done.sh` (the `own_date`/`prior_done` branch, around line 119):

    if own_date is not None and own_date > cutoff:   # id:5355 -- explicit recent date wins
        ym = None
    elif line.rstrip('\n').strip() in prior_done:    # <-- undated lines fall to here
        ym = today_ym

The `id:5355` fix keys on an **explicit trailing date**. `id:1975` had none, so it fell straight
through to the prior-commit branch -- and the mandated `git-diary-workflow` -> `todo-update`
order guarantees a same-session close IS in "the prior commit" by the time the archiver runs.
So the hazard `id:5355` was filed to prevent is still fully live for any closed item without a
trailing date. CLAUDE.md's own gotcha states the guard as "an item's OWN trailing date wins over
the prior-commit rule", which is accurate and also the whole problem: no date, no protection.

`id:aedf` was swept the same way earlier in this session. That one was harmless -- no `routed:`
marker -- which is precisely why it was not noticed as a symptom.

## Workaround used, so it is not mistaken for the fix

The line was restored to `TODO.md` by hand and given a trailing `on 2026-09-10`, which the
archiver now declines to sweep (verified: a re-run reports "nothing to archive or prune"). That
is a per-item sticking plaster, not a fix -- it depends on whoever files a cross-repo twin
remembering to date it.

## Two candidate fixes, and the recommendation

1. **Make the archiver refuse to sweep a line carrying a `routed:` marker** while its source
   inbox line is still open. Keeps the twin where the guard looks. Needs care: "still open" is
   cross-repo state, and the inbox is local-only to public repos, so the archiver must take its
   path by injection (`$RELAY_INBOX`) and fail OPEN (archive nothing) when it cannot read it.
2. **Widen the twin check to `TODO.archive.md`.** One line in `append.sh`, and arguably more
   correct: an archived closed item IS a durable record of landing, which is what the twin is
   supposed to attest.

**Recommended: (2) as the immediate fix, then (1) as defence in depth.** (2) is a one-line change
to the predicate that was wrong, it cannot break an unrelated path, and it fixes every already
archived twin retroactively -- there may be others, since this has been possible for as long as
both mechanisms have coexisted. (1) is the better invariant but it reaches across repos and
fails in more ways.

Not yet checked, and worth checking before choosing: whether any PAST `routed:` twin is already
sitting in `TODO.archive.md` with its inbox line still open. That is a measurement, and it also
tells you whether (2) alone is sufficient.
