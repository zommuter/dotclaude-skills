## From ROADMAP

### The conflict

The ledger line grammar (`id:b048`) says an item line ENDS at its anchored id marker --
nothing after it, not even a trailing space. The archive convention appends a stub AFTER
the whole line: ` (archived -- see ROADMAP.archive.md)`.

Both are load-bearing, and they cannot both hold.

- The stub is WRITTEN by `relay/scripts/roadmap-archive.sh:114` and
  `relay/scripts/archive-closed.sh:107`.
- It is PINNED by **7 test files**.
- It accounts for roughly 55 of the 79 `grammar-item-after-id` findings in `ROADMAP.md`.

The remaining ~24 `after-id` findings are other trailing text and are a separate question;
this item is about the stub.

### Why it was refused rather than fixed

The `id:40c0` migration left all 79 in place. Moving the stub before the id marker means
editing two writers and all seven tests, which is a change to an established convention
rather than a cleanup, and `tests/` was outside that agent's write scope. Refusing and
reporting was correct.

### The options

1. **Move the stub before the id marker.** The grammar wins. Costs two writer changes and
   seven test updates, and every already-archived line stays non-conforming until rewritten
   (or is grandfathered, since archives are out of grammar scope anyway).
2. **Exempt the archive stub in the grammar.** One narrow, documented exception for a
   fixed literal. Cheap, and honest that this is a real convention -- but an exception in a
   three-shape grammar is precisely how a three-shape grammar becomes a five-shape one.
3. **Stop writing the stub.** The information (that an item was archived) may already be
   recoverable from the archive file itself, in which case the stub is redundant. Needs
   checking before it can be proposed seriously.

### Note on scope

`*.archive.md` is out of grammar scope (`todo-conformance.sh:700`, `id:2065`), so the stub
only matters on lines that carry it while still in a LIVE ledger. Worth measuring how many
of the ~55 are in that state versus already archived -- if the answer is few, option 3
becomes much more attractive and options 1 and 2 both shrink.

### Recommendation

Measure first, per the note above, then decide. I would not pick between 1 and 2 without
knowing how many live lines actually carry the stub. Option 3 is the one that dissolves the
problem rather than guarding it, which is the direction the CLAUDE.md design heuristics
prefer, and it is cheap to test.

## DECIDED 2026-09-03 -- owner-ratified: OPTION 2 (exempt the stub in the grammar)

**The recommendation above is SUPERSEDED, and its preferred option 3 is REFUTED.** This
section is an edit to a note that was authored directly (it carries no
"reproduced verbatim" claim, so nothing above is falsified by appending here).

### What the measurement actually showed

The note asked for a measurement and named the wrong one. Measured 2026-09-03:

- 68 live lines in `ROADMAP.md` carry the stub (0 in `TODO.md`).
- All 68 ids are present in `ROADMAP.archive.md` -- recoverability is 100%.
- The live line and the archived line are **byte-identical except for the stub**.

That last fact is what makes the recoverability figure irrelevant. The stub is not a
pointer a human follows to a fuller record; both copies are the same text.

### Why option 3 is unsafe, not merely unattractive

`roadmap-archive.sh:114` is the authority. **The stub is the archiver's IDEMPOTENCY GUARD.**
`stub_line_re` matches `^- \[x\] .*<!--\s*id:[0-9a-f]{4}\s*-->.*` + `STUB_SUFFIX`, and its
documented purpose is to stop the archiver eating its own output. Without it the archiver
deletes the stub, re-appends the body to `ROADMAP.archive.md`, duplicates ids there, and
re-blinds `orphan-scan --cross-ledger` (which reads ONLY the live file). Reproduced in the
fleet, per that comment block: loderite `id:154a` restored 59 stubs at `1dc91f6` and the
SAME relay run deleted 58 of them 12 minutes later; cartulary accumulated up to 9 duplicate
bodies per id. Option 3 reintroduces that defect. It is viable only if a different
idempotency marker is built FIRST.

### Why option 1 is more expensive than this note estimated

`stub_line_re` requires the suffix to follow the id marker. Moving the stub before the
marker breaks the regex -- and that regex is deliberately mirrored from loderite's
`tools/archive-roadmap.mjs` (`STUB_SUFFIX` / `STUB_LINE_RE`). So option 1 is not "two
writers and seven tests"; it is a cross-repo breaking change to a fleet-mirrored guard that
must land in both repos simultaneously, or the two archivers disagree and re-archive each
other's output.

### The ruling

**Option 2.** One documented exception admitting the fixed literal `STUB_SUFFIX` after the
id marker. Rationale, in the owner's terms: the stub is a **machine-read guard token, not
prose**. The grammar's "line ends at the id marker" rule exists to stop prose sprawl, and
the grammar already admits structured markers (typed-edge comments) on an item line. The
wedge risk this note raises is real but is bounded by the exception being a FIXED LITERAL
rather than a shape -- nothing else becomes admissible by it.

Touches no writer and no test, and does not desync from loderite.

**Implementation owed:** `todo-conformance.sh`'s `grammar-item-after-id` class must exempt
a trailing `STUB_SUFFIX`. Note the guard regex is deliberately NOT end-anchored (real stubs
carry trailing annotations past the suffix -- live examples `bfb3`/`3d6c`/`a10c`), so the
exemption must not be end-anchored either or it will miss exactly those. The ~13 non-stub
`after-id` findings in `ROADMAP.md` are a SEPARATE question and are NOT covered by this
ruling.

**There is no single literal to source, and that is the first thing to fix.** Measured
2026-09-03: `todo-conformance.sh` has ZERO stub awareness (no match for `archived` or
`STUB`), and `STUB_SUFFIX` is spelled INDEPENDENTLY in **two** writers --
`relay/scripts/archive-closed.sh:107` and `relay/scripts/roadmap-archive.sh:114` -- each
with its own copy of `STUB_LINE_RE` (`:123` and `:122`). Adding the exemption naively makes
the checker a THIRD copy, and a fourth already exists off-repo in loderite's
`tools/archive-roadmap.mjs`. That is precisely the failure `id:4983` closed for the lane
grammar ("the lane grammar is hand-mirrored in three places; make ONE source serve both the
actor and the checker"), so this exemption should land the same way: one shared definition
that both writers and the checker consume. Doing it as a third literal would satisfy this
ruling while recreating the defect a sibling item was closed to remove.

**Do NOT hand-fix the em dash inside `STUB_SUFFIX`.** The literal is
`" (archived — see ROADMAP.archive.md)"` and it contains an em dash, which the fleet style
rule bans in new prose. It is SYNTAX here, matched by the archivers on both sides of the
fleet, so changing it in isolation silently desyncs the guard -- the `id:d35a` no-op class.
It migrates only when every mirrored copy migrates together.

That ruling's premise -- that the stub is a machine-read guard token which must therefore be

already excluded.

Two facts from this note survive intact and are load-bearing elsewhere:
- The em dash inside the legacy literal is SYNTAX, not prose. It is retained verbatim in
  `relay/scripts/lib-archive-idempotency.py` as `LEGACY_STUB_SUFFIX` (read half only) so that
  stubs written before this change, here and across the fleet, are still recognised and never
  re-archived. Do not hand-fix it.
- loderite's `tools/archive-roadmap.mjs` still emits the old convention, so the two archivers
  now DIVERGE. There is no runtime coupling (each repo archives its own ledger), but the
  divergence needs routing to loderite rather than discovering.
