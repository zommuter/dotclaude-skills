## From TODO

Found 2026-09-03 while reading `id:ee62` for the `id:14e5` filing.

### The defect

`tools/ledger-shrink.py`'s keep-set carries a STRUCTURAL catch-all, `<!--[^>]*-->`, so that
any marker minted later is preserved without the pattern list being updated. That rule is
correct and was adopted deliberately (loderite adopted it FROM us at `c5d78046`).

**It cannot distinguish a REAL marker from a marker QUOTED AS AN EXAMPLE in prose.** When an
item's body discusses marker syntax, the shrinker hoists the examples onto the head line as
if they were the item's own markers.

### The damage, measured

`TODO.md:34` -- `id:ee62`, whose subject is literally "use visible annotations, not HTML
comments" -- now reads (abridged):

```
- [ ] [INPUT - meeting] **Use VISIBLE annotations…** -- detail: `docs/ledger-notes/ee62.md`
  <!-- id:XXXX --> <!-- routed:XXXX --> `@manual` <!-- xledger-ok:"*` at ~L63/72; back-compat
  or one-shot migrate); (3) update `tests/test_ledger_seam.sh`; … <!-- id:ee62 -->
```

Three separate failures on one line:

1. `<!-- id:XXXX -->` and `<!-- routed:XXXX -->` are the note's EXAMPLES, hoisted as markers.
2. `` `@manual` `` was hoisted out of prose by the same keep-set.
3. The `<!-- xledger-ok:` example is UNTERMINATED in its own right, so the catch-all matched
   through to the next `-->` far away and **dragged ~300 chars of prose onto the head line**
   -- defeating the shrink for this item entirely.

**30 ledger lines** carry a placeholder marker of this shape: 28 in `TODO.md`, 2 in
`ROADMAP.md`. Not all are as damaged as `ee62`; the census is the first task.

### Why it did not fire an alarm

The hoisted tokens are not valid ids -- `XXXX` is not `[0-9a-f]{4}` -- so no owning-marker
check sees them and `id:6059`'s multi-marker refusal does NOT fire. The line remains
writable by `md-merge`. **Verified**: an `md-merge.py update-ids --append` against `ee62`
resolves to line 34 and writes correctly. So the corruption is cosmetic to the tooling and
invisible to every existing guard -- it only degrades the ledger for a human reader, and it
silently defeats the shrink.

### The fix, and its coupling

Mask backticked spans, and/or require that an example marker be backtick-escaped, before the
keep-set runs. **That escape convention is `id:14e5`(3)**, so the two are the same rule seen
from the tool side and the syntax side. Fixing this is arguably a prerequisite for `14e5`:
that migration rewrites every marker in the corpus and would propagate the corrupted lines.

**Beware the opposite convention** (`id:1254`): `classify-repo.sh` does NOT mask backticks,
so a backticked lane bracket IS the computed lane today, and `tools/roundtrip-validate.py`
(`id:ff7c`) deliberately mirrors that. Masking here and not there is defensible -- a lane and
a marker are different objects -- but it must be a stated decision, not an accident of which
file got edited.

- **Acceptance**: `ledger-shrink.py` does not hoist a marker that appears inside an inline-code
  span; a census of the 30 affected lines with each classified as damaged or benign; the
  damaged ones repaired. A test pins the `ee62` line shape specifically.

- **Done-check**: re-running the shrinker over a fixture built from `ee62`'s original body
  produces a head line carrying only that item's own markers, and `tests/` covers the
  unterminated-example case that dragged 300 chars.
