## From TODO

**The incident, measured rather than inferred.** Run `relay-20260908-231617-32609`
(`--afk --execute-agent-type relay-implementer`) stopped advancing at **01:36:48 on
2026-09-09** and never resumed. Its last in-flight child, `agent-ae932ecfc6732dad3`
(execute unit on dotclaude-skills, `relay-implementer`/sonnet), ends its transcript on a
`tool_use` block with **no `tool_result` following it**:

```
cd ~/.cache/relay/worktrees/dotclaude-skills/relay-20260908-231617-32609-execute-repo-0 \
  && git checkout -- tools/shrink-acceptance.py && git status --porcelain
```

`~/.claude/settings.json` lists `Bash(git checkout -- *)` under `permissions.ask`, and the
command is a compound `cd … && …` chain besides, which matches no allowlist pattern. Either
route requires a human decision. At 01:36 on an unattended run there was nobody to give one,
so the child blocked on the prompt, the parent loop blocked on the child, and the run sat
there until the clean shutdown at **03:53:38**.

**What the evidence rules OUT, so it is not re-derived.** Every proxied HTTP response in the
window is 200. There is no crash, kill, or segfault entry in the journal. The only OOM
(01:03:45, `relay-mech.slice`) is a **test fixture** -- `python3 -c "x = bytearray(600*1024*1024)"`
sitting beside `/bin/true` and `exit 42`, i.e. the mechanical-run sandbox suite, not the pool.
And `hooks/destructive-git-guard.py` is **not** the cause: it denies only the five tree-wide
forms and explicitly allows `git checkout -- path/to/one/file.sh`.

**Why this is worse than one lost run.** The hang is invisible to every counter the relay
keeps: `agent-failures=0` throughout, the child stays `in-flight` forever, and no handback is
ever produced. Nothing times out. The only mechanism that noticed anything was the `id:98f0`
outage watchdog, and it can only speak after a full 3600s heartbeat TTL (it fired correctly at
02:13:19, one TTL after the 01:13:02 beat). So the floor on detecting a wedged unattended pool
is currently one hour, and the signal it emits is "dead", which is the wrong diagnosis -- the
session was alive and waiting.

**The disposition is the owner's, and the obvious fix is the dangerous one.** Three shapes,
none free:

1. **Auto-deny any `permissions.ask` match under `--afk`.** Safe, and it converts a silent
   hang into a normal tool error the child can report. But it changes the meaning of `ask`
   for a whole class of commands, and a child that gets a deny may route around it -- which
   is the `no-route-around` failure the owner named on 2026-08-26.
2. **Pre-approve a narrow set for pool children.** This is the one to be careful with:
   `git checkout -- <file>` is exactly the destructive class the owner ruled on
   **2026-08-22 (unconditional deny, do not re-litigate)**. Widening it for unattended
   children is a request to relax that ruling in the least supervised context there is.
   Note the irony that makes the case concrete: the child hung *while trying to discard*
   `tools/shrink-acceptance.py`, so 181 lines of uncommitted work in
   `…-execute-repo-0` survive only because the prompt blocked it.
3. **Fail-fast handback on any prompt.** A child that cannot proceed without a decision
   hands the item back with the pending command named, and the pool moves on. Most faithful
   to "surface, don't act", and it needs a detection hook that does not exist yet.

Whatever is chosen, the **detection** half stands on its own and is not a decision: a child
that has issued no tool result for N minutes should be surfaced as wedged rather than counted
as in-flight, and the watchdog's verdict vocabulary needs a state between "alive" and "dead".

## UPDATE 2026-09-09 -- option 2 is far cheaper than it looked, and needs no ruling relaxed

The owner asked whether the deny could apply only to a **literal wildcard** checkout and not a
specific one. **It already does.** `hooks/destructive-git-guard.py` was exercised directly
rather than read, and its verdicts are exactly the wanted shape:

| command | guard verdict |
|---|---|
| `git checkout -- .` | DENY |
| `git checkout -- *` | DENY |
| `git checkout -- tools/foo.py` | ALLOW |
| `cd /tmp/x && git checkout -- .` | DENY |
| `cd /tmp/x && git checkout -- one.py && git status` | ALLOW |

So the guard is **not** what prompted the wedged child, and the 2026-08-22 unconditional-deny
ruling does **not** have to be relaxed to fix this. The prompt came from
`~/.claude/settings.json`, which lists `Bash(git checkout -- *)` under `permissions.ask` --
a pattern wildcard that matches the safe single-file form too. That entry is pure redundancy
against the hook, and its only remaining effect is the false prompt that hung the pool.

**The change:** delete `"Bash(git checkout -- *)"` from `permissions.ask` and add the same
string to `permissions.allow`. Tree-wide forms stay denied by the hook (a PreToolUse deny
outranks a permission allow), specific-file forms stop prompting. The hook is a sound sole
guard here: `find_violation()` is documented `NEVER raises (id:3866)` and routes any internal
failure to a conservative regex scan rather than failing open.

**APPLIED 2026-09-09 on the owner's explicit second instruction** (`~/.claude` commit
`8fa066f3f`). A first attempt the same session was refused by the auto-mode classifier as the
auto-mode-bypass class -- the CLAUDE.md "never self-edit `permissions`" rule enforced in the
harness rather than merely written down -- and the half-applied removal was reverted rather
than routed around. It went through once the owner had asked for it directly.

Final shape, covering `restore` as well as `checkout` on the owner's instruction: both broad
patterns moved to `allow`, and the tree-wide spellings the pattern language CAN express added
to `ask` as EXACT matches (`git checkout -- .`, `git checkout .`, `git restore .`,
`git restore --staged .`, `git restore -S .`).

**Verified by running it, not by reading it:**

| invocation | result |
|---|---|
| `cd <repo> && git checkout -- f.txt` (the exact incident shape) | ran, **no prompt**, file restored |
| `cd <repo> && git checkout -- .` | **refused** by the guard, canary file survived |

An earlier attempt at this verification was inconclusive and is worth recording, because it
demonstrates the very gap: `git -C <path> checkout -- f.txt` was auto-approved, but NOT by the
new rule -- prefix matching is positional, so `git -C … checkout` does not match
`Bash(git checkout -- *)` at all. The test had to be re-run in the compound `cd … &&` shape to
exercise the rule. That is `id:69ea`'s thesis reproducing itself inside its own verification.

**What this does and does not close.** It removes the specific landmine that hung this run.
It does **not** close the class: ANY `permissions.ask` match still hangs an unattended child
forever, and `git reset --hard*`, `git clean -f*`/`-d*` and `git stash drop*`/`clear*` remain
broad `ask` patterns. The detection half (a child with no tool result for N minutes should be
surfaced as wedged; the watchdog needs a verdict between "alive" and "dead") is untouched and
is still the substance of this item. Do not tick `76e4` on the strength of the settings change.

## UPDATE 2026-09-09 (second): the `ask` list is SHADOWED, which is not the same as safe

Swept for anything else that could still hang an unattended child. Result: nothing can, on the
git surface, and the reason matters more than the result.

**All ten `permissions.ask` entries are unreachable.** Their thirteen real command forms
(`git reset --hard`, `… --hard HEAD~3`, the five tree-wide checkout/restore spellings,
`git clean -f`/`-d`/`-fd`, `git stash drop`/`drop stash@{0}`/`clear`) were each run through
`hooks/destructive-git-guard.py`: every one denies. The hook is PreToolUse, so it fires BEFORE
the permission layer -- demonstrated rather than assumed, since `git checkout -- .` (which IS
an `ask` entry) returned the guard's refusal and not a dialog.

Supporting sweep, all negative for a hang: none of the three PreToolUse hooks can emit `ask`
(`destructive-git-guard` and `rm-force-guard` return `permissionDecision: deny`,
`pathspec-drop-guard` returns `decision: block`); auto mode DENIES rather than prompts (twice
observed this session); the one true hang vector, `sudo -A` with a graphical askpass, exists
only in `provision-relay-users.sh`, which has ZERO references from `relay-loop.js` and
`relay/SKILL.md` (`deny-tail-probe.sh` uses non-interactive `sudo -n`); no relay script invokes
any denied form, and `relay-loop.js:3570` already forbids children to; and delegated subagents
carry no `AskUserQuestion` in their tool roster, so a child cannot ask the owner anything.

**So what are the `ask` entries still for?** They are a backstop in a DIFFERENT FAILURE
DOMAIN, and they should be kept. A PreToolUse hook that fails to LOAD is non-blocking --
`find_violation()`'s own docstring records that a hook exiting non-zero makes Claude Code print
stderr and RUN the command -- so an unwired, renamed, or `disableAllHooks`-suppressed guard is
silently absent, and then the `ask` entries are the only thing standing between an agent and an
unrecoverable tree-wide wipe. Their failure mode in that world is a HANG, which is strictly
better than the loss they prevent. Keep them; just do not mistake them for the mechanism.

**The rot risk, and the cheap fix.** A shadowed rule is an untested rule: nothing asserts that
the `ask` list and the guard's blocked-form list still agree, and they can drift in either
direction (an `ask` entry the guard stops covering silently becomes a live pool-hang; a guard
form with no `ask` twin loses its backstop). This is a one-fixture job in a repo that already
has the harness: assert every git entry in `permissions.ask` is denied by
`destructive-git-guard.py`. Filed as a recommendation, not built.

**The interaction that would re-arm this item.** A worktree exemption for the guard would
UN-SHADOW the `ask` entries precisely in the context where pool children run, restoring the
exact hang this note is about. `hooks/README.md:37` calls that exemption "TODO id:6a6b", but
**`id:6a6b` is not an independently trackable item**: the marker sits at the end of a
CONTINUATION line inside the sandboxing item at `TODO.md:917`, not on a checkbox head, so no
scanner surfaces it as open work. If that exemption is ever built, the `ask` entries must be
revisited in the same change.
