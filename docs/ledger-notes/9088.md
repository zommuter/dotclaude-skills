**The defect.** Case 3 asserts that a "rewritten but STILL over budget" item is refused --
the whole point being that editing a title without actually shortening it must not pass. Its
fixture (`tests/test_title_rewrite_batch_acceptance_64f9.sh:138`) is:

```
A1_BOTCH='- [ ] [ROUTINE] **Alpha** the title on this line is still a whole paragraph rather
than a title and remains well past the two hundred character budget, having been edited
without actually being shortened at all <!-- id:a1a1 -->'
```

The prose claims it "remains well past the two hundred character budget". It does not.
Measured after the same stripping `todo-conformance.sh`'s grammar check applies (drop the
checkbox, the lane tags and the HTML comments): **194 characters**, against
`LEDGER_ITEM_TITLE_MAX=200`. So `todo-conformance.sh` classifies it `shape-new` and NEVER
emits `grammar-item-title-long` -- the very finding case 3 waits for. The fixture is a
SUCCESSFUL rewrite masquerading as a botched one.

**Confirmed twice, independently.** A review agent found it by running the spec (it dies at
assertion 3, with cases 0/1/1b/2 passing and 4-7 never reached) and by feeding the exact line
to the conformance script. Re-derived here by measuring the string directly: 194. When the
fixture is lengthened past 200 in a throwaway copy, cases 3, 4, 5 and 6 pass.

**Why this is filed separately.** It is a bug on MAIN, in the RED spec itself, independent of
any implementation. An executor will implement the check correctly and still watch case 3 fail,
with nothing in the failure output suggesting the fixture rather than the code is wrong. That
is the expensive shape -- a red test that lies about which side is broken.

**WHICH ITEM IT BLOCKS -- corrected 2026-09-09, this note first said `id:64f9`.** Two ids are
in play and they are not interchangeable:
* **`id:521b`** (`ROADMAP.md:186`, open `[ROUTINE]`) is the item that IMPLEMENTS the check, and
  is what an executor is actually dispatched at. **This is the item this bug blocks.**
* **`id:64f9`** (`ROADMAP.md:165`, open `[INPUT - decision]`) is the DECISION item ("257 ledger
  items have a title that is itself over budget"), auto-gated `route:hard-split` and decomposed
  into seams `id:521b` and `id:b437`, with its own line saying *"pick those, not this"*. No
  executor is dispatched at it.
The confusion is easy to make and worth stating: the spec FILE is named `..._64f9.sh` and
declares `# roadmap:64f9`, so the suite's expected-red bookkeeping keys on **`id:64f9`**'s
checkbox while the WORK keys on `id:521b`'s. Both are open today, so the test correctly reports
`EXPECTED-RED` -- but a reader who ticks `521b` on completion will find the spec still
classified expected-red against `64f9`, and a reader chasing `64f9` finds a gated decision item
with no code to write. Fixing the fixture does not resolve that split; it is noted here so the
next person is not surprised by it.

**It also silently truncates the spec's coverage.** The runner stops at the first failing
assertion, so cases 4-7 have NEVER executed. Whatever they assert is unverified today, and
fixing case 3 will expose them for the first time -- expect further failures, and read them as
newly-reached rather than newly-broken. (One is already known: case 7's LEFT-item report is
emitted as a plain line that `--quiet` filters out, which is a genuine implementation gap, not
a fixture bug.)

**Fix:** lengthen `A1_BOTCH`'s title past 200 characters so the case exercises what it claims.
**Acceptance:** the case fails against an implementation that accepts a still-over-budget
rewrite, and passes against one that refuses it -- i.e. it discriminates, which today it
cannot. **Done-check:** `tests/run-tests.sh tests/test_title_rewrite_batch_acceptance_64f9.sh`
reaches case 7; `make test` green.

**Do not "fix" it by lowering the budget or loosening the assertion** -- the case is right and
the fixture is wrong. This is the id:292b/a73c family: a negative case that cannot fail for the
declared reason is exactly as vacuous as one that passes for the wrong one.
