## 1. READ FIRST — `id:99b7` is NOT a bookkeeping item

It was filed this morning as *"the ratification queue mints entries that can never resolve"* —
queue hygiene. **It is actually: on a non-substantive unit, the relay pushes to every remote it
can reach, including a third party's repository.**

Code-confirmed at `relay/scripts/integrate.sh:845-852`. The only per-remote opt-out is a push URL
set to the literal string `no_push`; otherwise, when `defer_push` is empty (a **non-substantive**
unit), every remote enters `to_push` — the comment says it verbatim: `# non-substantive: push
everything`. For `git-annex` that is `git push upstream` against `git://git-annex.branchable.com/`,
**the upstream project this repo forks**.

Not theorised — **observed**. While authoring the `99b7(a)` RED spec, a fixture used the real
upstream URL and scenario D's non-substantive path actually attempted the push. git-annex's
pre-receive hook rejected it. Nothing was published (`git://` is read-only there), the fixture was
replaced with a local bare repo, and the agent disclosed it plainly.

The **substantive** path is not affected — it defers non-private remotes for ratification, which is
how the four unresolvable entries got minted. Same root cause, two symptoms, very different weight.

**STOPGAP IS APPLIED** (owner-ratified): `git -C ~/src/git-annex remote set-url --push upstream
no_push`. Because `:846` `continue`s *before* `eligible_count` increments, this kills both symptoms
— no push attempt on a non-substantive unit, no `pending_remotes` entry on a substantive one. The
FETCH url is deliberately unchanged, so tracking upstream still works. Revert with
`git -C ~/src/git-annex remote set-url --push upstream git://git-annex.branchable.com/`.

**The lesson, three times in one day:** every real defect today surfaced from *running* something,
never from reading it — rule 2c's total inertness, the multi-line-marker bug, and this. Each looked
well-understood on paper first.

## 6. Gotchas learned today

- **`grep -m1 -o` bounds matching LINES, not matches.** A real dispatch prompt names the worktree
  twice ("Your worktree `<wt>` … on branch relay/`<wt>`"), so the marker came back as a two-line
  string and silently matched nothing. Trim with `${m%%$'\n'*}`, never `| head -1` (the id:81d5
  banned shape).
- **Check WHICH marker failed before reporting a resolver defect.** Three "matched none" hits in a
  run were the literal placeholders `'$marker'` and `'<worktree basename>'` — quoted text from the
  script's own error template and from a TODO item, appearing in transcripts because agents *read*
  those files. Counting failures would have invented a defect.
- **`ratify-queue.sh verify` picks the wrong remote for a fork.** It defaults to the entry's
  recorded `pending` remote; for git-annex that was `upstream`, so `--remote origin` is REFUSED as
  "does not cover this entry's PENDING remotes". The refusal is correct — the entry itself was
  mis-minted.
- **A queue length is not a work count.** The "13 pending, oldest 4 days" backlog was 12 pieces of
  bookkeeping and one void entry. Six were already published and never `resolve`d.
- **`git cherry` reports textual drift, not substance.** All 5 parked orphans showed `+` while every
  one was fully superseded. Verify per-id and per-artifact instead.
- **Nothing reads `salvage/*` tags.** `relay-reconcile.sh` enumerates `refs/heads/relay/*`;
  `death-record.sh`'s salvage probe globs worktrees and branches; the tag readers filter to
  `*-ckpt-*`. A park-then-tag commit is preserved forever and surfaced never.
- **A test in this repo reached the network** (the spec fixture push, §1). Hermeticity is a rule
  here; a fixture holding a real remote URL will act on it.
