  - **Field report — zkWhale demo-chain run, 2026-06-17/18 (~20 background agents, directed `/relay --afk`):** Ran ~20 worktree children in waves of 1–3, integrated sequentially (merge → full gate → ckpt-tag → push) ≈20×. Octopus's win here is halving *gate-runs + pushes* for co-ready disjoint waves, more than the tag/log noise. (2) **Octopus opportunities genuinely arose ~4–5×** (THEME+emoji-svgs; spinrot+logofix; the two logo rounds; proofglyph+badgesvg) — each ≥2 branches, file-disjoint, individually green, finished within minutes. (3) **The octopus-blockers that actually recurred were a small set of high-churn shared files:** `strings.ts` (almost every UI agent appends copy — distinct keys so git *auto-merged*, but it's the #1 risk), `package.json`/`pnpm-lock.yaml` (new devDeps: vite-plugin-singlefile, jimp, potrace), hot UI files like `ArtifactScreen.tsx` (touched by demo-mount/spinner/emphasis across waves), and the ledgers (`TODO.md`). (4) **Deterministic eligibility predictor that would've worked:** pairwise-intersect `git diff --name-only main..<branch>` across the co-ready candidates; empty intersection ⇒ octopus-safe. (5) **Granularity downside barely bit this workload** — every track was gate-verified *before* merge, so I never needed to bisect/cherry-exclude a track post-integration; a well-formed combined ckpt message preserved the attribution that per-track tags gave. (6) **Recommended impl:** optimistic octopus — `git merge --no-ff b1 b2 …` (git refuses cleanly on conflict, no half-merge), fall back to sequential for the conflicting subset; gate ONCE after the merged result; run `pnpm install` once if any branch touched the manifest (orthogonal to merge strategy but required before the gate). Net: for this run, a file-intersection-gated optimistic octopus would have cut ~5–7 of the ~20 integration cycles (~30%) with negligible downside. (field report 2026-06-18)
